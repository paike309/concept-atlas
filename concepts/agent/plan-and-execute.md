## 一句话定义

**中文**：先让模型产出完整计划，再逐步执行，执行中按需修正的 Agent 结构。

**English**: An agent structure that produces a full plan up front, executes it step by step, and revises it when needed.

## 我的理解

它与 [ReAct](react-and-planning.md) 的差别是**决策频率**：ReAct 每一步重新决策，Plan-and-Execute 只在开始时决策一次、中途偶尔修正。

- **好处是全局性**：能先看到完整路径再动手，避免"走到一半才发现方向不对"
- **代价是对初始信息的依赖被放大**：一开始的信息不足或有误，整份计划都会系统性偏离；而且因为计划是结构化的，纠正成本比逐步试探更高

所以适用条件很明确：**任务的中期状态可预测。**

可预测时才值得提前规划；不可预测时，详细计划是负担。这与"能列出确定步骤就该用 Workflow"是同一条判断的延伸。

## 核心机制

**三个阶段**：规划（产出步骤列表）→ 执行（逐步调用工具）→ 修正（计划失效时重规划）。

**计划的表示**：自然语言清单、结构化步骤（含依赖）、或状态机。**结构化程度越高，越容易被程序检查与修正。**

**重规划的触发条件必须显式定义**，例如：

- 连续两次工具失败
- 观察到与计划前提矛盾的信息
- 步骤超时

**没有触发条件，就会照着错计划走到底**——这是这类结构最典型的失败方式。

**与 ReAct 的混合**：外层用计划提供全局约束，内层每一步用 ReAct 处理局部不确定性。

**计划的粒度**：过细会让计划本身成为负担（维护成本超过收益），过粗等于没有计划。

## 边界：它不是什么

- **与 [ReAct](react-and-planning.md) 的区别**：决策频率。一个每步都re-decide，一个只在开始与少数节点重新决策。
- **与 [Workflow](agent-loop.md) 的区别**：计划的产生者是**模型**，不是人。人可以审查计划，但计划不是预先写死的。
- **与"任务分解"的区别**：分解把任务拆小；规划还包含**顺序与依赖**。

## 常见误解

1. **先规划总是更好** → 信息不足时，详细计划会锁死错误方向。
2. **计划生成后要严格执行** → 必须定义重规划条件，否则错得很彻底。
3. **计划越详细越好** → 粒度过细会降低适应性，也增加维护成本。
4. **它比 ReAct 更可靠** → 它改变的是**误差累积的方式**，不是消除误差。

## 应用场景

- **该用**：中期状态可预测、步骤多且依赖明确、需要先向用户展示计划以获得确认
- **不该用**：路径高度不确定的探索性任务
- **判断依据**：**能否在动手前写出步骤序列。** 能写，就值得考虑；写不出，就不要用
