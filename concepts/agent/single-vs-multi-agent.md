## 一句话定义

**中文**：用单个 Agent 循环完成全部工作，还是拆成多个 Agent 各负责一部分并协作的取舍。

**English**: The trade-off between one agent loop doing everything and splitting the work across several cooperating agents.

## 我的理解

先说结论：**多智能体增加的是并行度与职责隔离，不是能力上限。**

成本是真实的：

| 成本 | 来源 |
|---|---|
| 通信 | Agent 之间交换信息，而这些信息又占用各自的上下文 |
| 一致性 | 并行工作会分叉，需要协议收敛（谁说了算、冲突怎么解） |
| 可观测性变差 | 轨迹从一条变成多条交织，调试难度显著上升 |
| 重复劳动 | 没有共享状态时会重复搜索同样的信息 |

所以判断标准很清楚：**只有当一个任务能干净地切成互不依赖、且各自有独立上下文需求的部分时，多智能体才划算。**

直觉上的"分工更专业"往往不成立。多数情况下，**单 Agent 配好工具 + 清晰的任务分解，效果更好且更容易调试。**

## 核心机制

**常见拓扑**：

| 拓扑 | 结构 | 风险 |
|---|---|---|
| 主管-工人 | 一个规划者 + 多个执行者 | 主管成为瓶颈 |
| 流水线 | 顺序传递 | 上游错误无损传递 |
| 辩论 | 多角色讨论后裁决 | 成本高、裁决机制易失效 |

**共享状态**：文件系统、共享内存、消息总线。**没有共享状态时，协调成本会迅速超过收益。**

**上下文隔离是它唯一的真实优势**：每个子 Agent 有独立上下文，不互相污染，也各自有自己的预算——这正好对应[上下文预算管理](context-budget.md)里"工作集太大"的那个问题。

**冲突解决**：必须有明确裁决机制（谁是主管，或按什么规则）。靠"让它们讨论"通常不收敛。

**与并行工具调用的区别**：并行工具调用是**同一个上下文**里的多个动作，不涉及上下文隔离。

## 边界：它不是什么

- **与并行工具调用的区别**：是否隔离上下文。这是最容易被混淆的一对。
- **与微服务的区别**：微服务按**部署与故障隔离**划分；多智能体按**上下文与职责**划分。两者正交。
- **与"人机协作"的区别**：人机协作里有一方是人，与多 Agent 的协作成本完全不同。

## 常见误解

1. **多智能体总比单智能体强** → 增加的是并行度，不是能力上限。
2. **角色越多越专业** → 角色是提示词层面的设定，不赋予新能力。
3. **它是并行的自然选择** → 并行不等于更快，协调开销常吃掉收益。
4. **多智能体解决了上下文限制** → 确实隔离了上下文，但引入了协调成本；净收益需要实测。

## 应用场景

- **该用**：任务可清晰切分且各部分需要独立上下文；需要多种互不干扰的专长；需要独立预算与故障隔离
- **不该用**：任务小、步骤强耦合、需要全局一致视图
- **判断依据**：**先尝试单 Agent + 好工具。只有在"上下文污染"或"预算隔离"成为实际瓶颈时，才拆。**
