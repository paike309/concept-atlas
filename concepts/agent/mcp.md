## 一句话定义

**中文**：把「AI 应用」与「工具、数据源」之间的对接标准化的一套开放协议。

**English**: An open protocol that standardizes how AI applications connect to tools and data sources.

## 我的理解

它解决的是 **N × M 问题**。

没有协议时：N 个模型应用要对接 M 个工具，写成 N × M 份集成代码。有了协议：工具方实现一次服务端，所有支持协议的应用都能用，变成 N + M。这是纯粹的接口经济学。

类比 USB-C 是对的，但容易理解偏。USB-C 统一的是**物理接口**，MCP 统一的是**能力描述与调用约定**——工具怎么声明自己、参数长什么样、结果怎么回。

**真正的贡献在于"工具描述"这一层被标准化了**，而不是"调用"本身。这一点值得记住，因为它解释了为什么 MCP 的价值随工具数量增长而增长，而不是随调用量增长。

## 核心机制

**三个角色**：

| 角色 | 是什么 |
|---|---|
| Host | 宿主应用（用户实际使用的那个） |
| Client | 宿主内部的连接器，与某个 Server 一对一 |
| Server | 提供工具或数据的一方 |

**三类能力**：

1. **Tools** — 可调用的动作（有副作用）
2. **Resources** — 可读取的数据（只读）
3. **Prompts** — 预置的提示模板

**传输**：本地用 stdio（子进程），远程用 HTTP 流式。连接时会做能力协商，双方声明支持什么，避免版本错配。

**权限边界**：Server 是**外部代码**，调用它意味着真实的系统权限与副作用。确认点与最小授权必须由 Host 承担——协议本身不提供安全保证。

## 边界：它不是什么

- **与 REST API 的区别**：API 描述"资源与操作"，面向程序员；MCP 额外描述"模型该怎么判断何时调用"，面向模型。消费者不同，描述的写法就不同。
- **与函数调用（Function Calling）的区别**：函数调用是**模型侧的输出格式**（模型说"我要调这个"）；MCP 是**工具侧的接入标准**（工具怎么被找到、怎么被声明）。两者互补，不是替代关系。
- **与插件系统的区别**：插件通常绑定特定宿主；MCP 面向跨宿主。

## 常见误解

1. **MCP 是模型能力** → 它是外部协议。模型不因为接了 MCP 而变强，只是多了可用的手段。
2. **接了 MCP 就等于安全** → Server 是第三方代码，具备真实的系统权限。装上不等于可信。
3. **同一个 Server 到处都能用** → 取决于 Host 是否支持相应传输与能力，且工具描述质量参差不齐。
4. **有了 MCP 就不用自己写工具** → 现成 Server 覆盖的是通用能力；业务逻辑仍然要自建。

## 应用场景

- **该用**：需要对接多个模型应用；工具生态会持续增长；希望第三方能接你的数据源
- **不该用**：单一应用对接单一内部接口——直接用函数调用更简单，少一层协议与进程
- **判断依据**：数一下"应用数 × 工具数"。接近 1 时不必引入协议；两者任一在增长时，协议带来的收益立刻显现

## 自测

1. N × M 变成 N + M，具体指什么？这个收益随哪个变量增长最快？
2. 为什么说 MCP 的 Server 是安全边界？装上它意味着接受了什么风险？
3. Tools、Resources、Prompts 三类能力，分别适合放什么内容？为什么把只读数据做成 Tool 是设计失误？
