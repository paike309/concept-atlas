## 一句话定义

**中文**：多个 Agent 之间如何交换信息、如何分工、以及一个失败时其它为什么会跟着失败。

**English**: How multiple agents exchange information, divide work, and why one failing tends to take others down with it.

## 我的理解

**多 Agent 的成本与风险不是"串联多个模型"，而是"把单点故障变成了一个故障网络"。**

一旦拆成多个 Agent，就出现了三个单 Agent 不存在的问题：

1. **信息在传递中被压缩。** 子 Agent 的完整上下文不可能全部传回父 Agent，只能传递摘要——**而摘要由模型生成，会丢信息、也可能出错**。父 Agent 基于摘要做决策，等于在二手信息上做判断。
2. **失败会放大而非抵消。** 一个子 Agent 给出错误结论，父 Agent 通常无法区分"它真查到了"和"它编了一个看起来合理的答案"。**多个子 Agent 的错误还会互相"印证"**——因为父 Agent 会把它们汇总成一个更自信的结论。
3. **成本与延迟是乘法关系。** 多个 Agent 各自消耗 token、各自调用工具，总消耗通常是单 Agent 的数倍（不同任务差异很大，不能假设"只多一点"）。**这也是它必须由任务价值来正当化的原因。**

由此得到两条实践结论：

- **协调的核心不是协议，而是"结果怎么被验收"。** 子 Agent 返回的内容必须能被**机械地校验**（结构化字段、可复核的引用、可执行的断言），否则父 Agent 只是在做一次"看起来有条理"的汇总。
- **故障传播路径必须被显式设计。** 子 Agent 超时、返回空、返回格式不符时，父 Agent 应当有明确分支：重试、跳过、还是整体失败。**默认行为如果是"把异常当普通结果处理"，系统会用错误结果继续往下走**——这比直接崩溃更危险。

## 核心机制

**三种常见协调结构**：

| 结构 | 形态 | 适合 | 风险 |
|---|---|---|---|
| 编排者—工作者 | 一个主 Agent 分派任务给子 Agent | 可并行、任务可拆分 | 主 Agent 成为瓶颈与单点 |
| 流水线 | 依次传递，后者接前者的产出 | 阶段清晰（研究 → 撰写 → 评审） | 上游错误全程传递 |
| 对等协作 | 相互通信直到达成一致 | 需要多视角辩论 | 难以收敛，成本不可控 |

**信息传递的三种携带方式**：

| 方式 | 说明 | 代价 |
|---|---|---|
| 完整上下文转发 | 保真度最高 | token 成本高，可能把噪声一起带过去 |
| 结构化摘要 | 父 Agent 只接收字段化结果 | **摘要即信息损失**，字段设计决定上限 |
| 共享外部状态 | 结果写入外部存储，各方按需读取 | 需要定义并发写与版本问题（见[共享状态与冲突解决](shared-state-and-conflict.md)） |

**失败传播的四种形态**（设计时必须逐一给出策略）：

1. 子 Agent 超时 → 重试或跳过，**不能让父循环无限等待**
2. 子 Agent 返回格式不符 → 重试一次，仍失败则降级为"该子任务未完成"
3. 子 Agent 返回错误结论（最难）→ **只能靠可校验的产出**（引用、断言、可执行验证）来降低概率
4. 子 Agent 之间结论冲突 → 需要预先定义**仲裁规则**（多数、权重、还是交由人工）

**预算与终止要按整体算**：多 Agent 场景下"每个 Agent 有自己的步数上限"是不够的——**总成本是所有分支之和，且随分工数增长**。必须有全局预算（token / 调用次数 / 时间），并在接近上限时**收敛而不是继续分裂**（见[终止条件与预算控制](termination-and-budget.md)）。

**可观测性要求比单 Agent 更高**：需要能把多个 Agent 的轨迹**串成一棵树**（谁分派给谁、各自花了多少、哪个分支导致了最终结论）。否则出问题时你只能看到一堆独立轨迹，无法定位责任环节（见[轨迹可观测性与回放](trajectory-observability.md)）。

## 边界：它不是什么

- **与[单 Agent vs 多 Agent 的取舍](single-vs-multi-agent.md)的区别**：那张卡回答"**要不要拆**"，这张回答"**拆了之后怎么不失控**"。取舍在前，机制在后。
- **与[结构化状态与外部存储](structured-state.md)的区别**：那张卡讲"状态放在上下文之外的哪里"，这张讲"多个 Agent 之间怎么传递与分工"。状态外置常是多 Agent 的实现手段，但两者解决的问题不同。
- **与微服务/消息队列的区别**：形态相似（分派、消息、编排），但**组件的可靠性性质不同**——微服务的接口是确定性契约，Agent 的"接口"是概率性的自然语言。**所以微服务里靠契约与重试解决的问题，在多 Agent 里不能直接套用。**
- **与"并行调用模型"的区别**：并发发起多个独立请求再汇总，是**并行**而非协作——没有中间的信息往返。它更便宜、更可控，**很多被设计成多 Agent 的场景其实只要并行**。

## 常见误解

1. **多 Agent 会"互相纠错"** → 更常见的是错误互相印证，因为汇总者无法判断来源可靠性。
2. **子 Agent 越多覆盖越全** → 协调开销、成本、失败面都随之增加；它们之间有明确的边际递减。
3. **子 Agent 的结论可以作为事实使用** → 除非能被机械校验，否则它仍是模型的输出。
4. **失败会自然暴露** → 演示时最典型的失败形态是"看起来完成了，只是答案是错的"。
5. **每个 Agent 各自设预算就够了** → 需要全局预算，否则分支一多总成本失控。

## 应用场景

- **该用**：任务可真正并行拆分、且**每个子任务的产出可被独立校验**（如多个来源的检索与核对）
- **不该用**：任务本身是线性的、或子任务产出无法验收、或成本敏感
- **判断依据**：问四句——**子任务能独立验收吗**？**摘要丢失的信息会影响最终决策吗**？**全局预算是多少**？**轨迹能串成一棵树吗**？
- **配套**：全局预算与终止条件、轨迹的父子关联、失败策略的显式定义

## 自测

1. 为什么"多 Agent 会互相纠错"通常是错的？错误的结论怎么会被放大？
2. 子 Agent 返回"格式不符"与"结论错误"，哪种更危险？为什么？
3. 为什么全局预算不能用"每个 Agent 各自的预算"替代？
