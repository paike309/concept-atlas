## 一句话定义

**中文**：对 Agent 系统（而不只是单次模型输出）的效果进行评测的方法。

**English**: Evaluating an agent system — not merely individual model outputs.

## 我的理解

与[模型评估](../ai/evaluation.md)有一条根本差别：**被评测的对象是轨迹，不是输出。**

由此推出三个特有要求：

**1. 要判过程，不只判结果。** 同样通过测试，一个用了 3 步一次成功，另一个绕了 15 步靠运气——**后者的可靠性完全不同**。所以指标必须包含步数、工具调用次数、成本。

**2. 要能重复跑。** Agent 非确定性，单次结果没有统计意义。必须多次运行看**成功率分布**。

**3. 环境要可控。** 依赖外部服务的 Agent 无法稳定评测，所以需要可替换的测试环境（模拟工具、固定数据）——这与[端口与适配器](../software/ports-and-adapters.md)的设计直接相关：**架构上留了端口，评测才可能受控。**

另外，由于 Agent 的失败有**类别**（见[失败模式](failure-modes.md)），评测集应该按失败模式覆盖，而不是随机采样任务。

## 核心机制

**三层指标**：

| 层 | 指标 |
|---|---|
| 结果 | 任务完成率、正确性 |
| 过程 | 步数、工具调用数、成本、时长 |
| 质量 | 是否达成目标、有无副作用 |

**成功率 + 分布**：同一任务集跑 N 次，看成功率与方差。**只跑一次的结果没有意义。**

**环境控制**：模拟工具（fake）固定返回值、固定时钟、固定随机种子。**可控环境是 Agent 评测的前提。**

**用例来源**（按价值排序）：

1. **真实失败案例回归集**——最重要，直接对应已发生的问题
2. 按失败模式构造的用例
3. 边界情形：空输入、超长输入、工具报错

**判定方式**：能用程序判定（结果文件、数据库状态）就不要用模型裁判。**过程指标天然可程序判定。**

**成本基线**：记录每次运行的 token 成本与时长，作为回归指标。**质量提升伴随成本翻倍不是改进。**

## 边界：它不是什么

- **与[模型评估](../ai/evaluation.md)的区别**：对象是**轨迹**而不是输出，因此需要环境控制与多次运行。
- **与集成测试的区别**：集成测试判"系统能不能用"，评测判"效果好不好"。
- **与[可观测性](trajectory-observability.md)的区别**：可观测性看**运行中的**系统；评测在**受控条件下**比较方案。

## 常见误解

1. **跑一次通过就算能用** → 非确定性系统需要多次运行。
2. **只看结果不看过程** → 绕 15 步成功与 3 步成功的可靠性不同。
3. **用真实环境评测** → 不可复现，环境波动会掩盖方案差异。
4. **用模型当裁判最省事** → 有偏置，且轨迹判定本来就适合程序化。

## 应用场景

- **该做**：任何要上线的 Agent；任何提示词 / 模型 / 结构改动的前后对比
- **判断依据**：能否回答"**改动之后成功率变了多少、成本变了多少、哪一类失败减少了**"。答不出，说明评测不到位
- **配套**：失败轨迹存档就是评测集的来源

## 自测

1. Agent 评测与模型评估的根本差别是什么？它带来哪些不同的要求？
2. 为什么必须多次运行？只看一次会得出什么错误结论？
3. 为什么成本与步数也要进指标？只有成功率会漏掉什么？
