## 一句话定义

**中文**：在固定的上下文窗口内，为系统提示、对话历史、工具返回、任务数据分配额度并持续回收的工程做法。

**English**: The practice of allocating and continuously reclaiming a fixed context window among system prompt, history, tool results, and task data.

## 我的理解

这是 Agent 长任务失败的首要原因，也是最容易被当成"参数调优"而不是"设计问题"的一环。

核心认识来自 [上下文窗口](../ai/context-window.md)：**Agent 没有状态变量，上下文就是它的全部状态。**

所以——**省上下文不是为了省钱，是为了保住它的记忆。**

一旦被截断，它会失忆、重复动作、目标漂移。而这些在外部表现为"模型变笨了"，极容易误诊成模型能力问题。**先查上下文占用曲线，再怀疑模型。**

## 核心机制

**四类占用**：

| 类别 | 特点 |
|---|---|
| 固定开销（系统提示 + 工具描述） | 每轮都在，且随工具数量增长 |
| 对话历史 | 只增不减，除非主动回收 |
| 工具返回值 | 增长最快、最不可控 |
| 当前任务数据 | 体量取决于任务 |

工具描述是**最容易被忽略的固定开销**：几十个工具的描述可能占掉可观比例，而且每一轮都要重放。

**回收顺序**（从最安全到最危险）：

1. **裁剪工具返回值**——去重、结构化、截断长文本。最安全，收益最大
2. **摘要较早的对话轮次**——有损，但损失可控
3. **丢弃已完成子任务的过程，只留结论**——需要确认该子任务不会回头
4. **压缩当前任务数据**——改成引用（路径、ID）而非全文

**不能回收的**：

- 系统提示与工具描述（除非重建会话）
- **当前任务的原始目标**——一旦被摘要就可能失真，这是目标漂移最常见的起点

**监控**：记录每轮的 token 占用**分布**，而不是只看总量。总量只告诉你"快满了"，分布才告诉你"该回收哪一类"。

## 边界：它不是什么

- **与"上下文窗口大小"的区别**：窗口是给定约束，预算管理是在约束内做分配与回收。**窗口再大也不能代替管理**——装得下不等于用得好（中段利用率下降、干扰增加）。
- **与"成本控制"的区别**：省 token 是副产品，主目标是保住状态完整性。反过来做（为了省钱而激进截断）会直接损害任务成功率。
- **与 [RAG](../ai/rag.md) 的区别**：RAG 决定"该拿什么进来"，预算管理决定"什么时候必须把东西拿出去"。一进一出，两个方向。

## 常见误解

1. **窗口够大就不用管** → 工具返回值的增长常常是超线性的；且长度越长，中段信息利用率越低。
2. **超了就截断最早的** → 最早的部分往往含**任务原始目标与关键约束**。截断它直接造成目标漂移，而症状要到很多轮之后才出现。
3. **摘要等于无损压缩** → 摘要是有损的，且由模型生成，会引入新错误。摘要再摘要会累积失真。
4. **这是框架的事** → 框架提供机制（截断、压缩），**分配策略属于业务设计**。

## 应用场景

- **该做**：任何多轮循环；任何工具返回值体量大的场景；任何单任务可能超过十轮的场景
- **判断依据**：跑一次典型任务，记录每轮的 token 占用曲线。**如果第 10 轮已接近上限的 80%，就必须设计回收策略**，而不是等它撞墙
- **配套**：把"每轮占用分布"纳入[轨迹记录](trajectory-observability.md)，否则出问题只能靠猜

## 自测

1. 为什么"截断最早的"是最危险的做法？它会以什么症状表现出来，为什么这个症状容易被误诊？
2. 工具描述为什么会成为固定开销的大头？有什么手段可以减少这部分占用？
3. 设计一个能提前发现目标漂移的监控指标。
