## 一句话定义

**中文**：把 Agent 的任务状态从上下文中抽出来，存成外部结构化数据（待办列表、状态机、数据库记录）。

**English**: Moving an agent's task state out of the context and into external structured data — todo lists, state machines, database records.

## 我的理解

这是对"上下文即状态"这一约束的**直接应对**。认识链条是一步步推出来的：

> Agent 没有状态变量 → 状态只能存在上下文里 → 上下文会满、会被压缩、会被污染 → **所以关键状态必须放到上下文之外。**

好处有三层：

| 好处 | 说明 |
|---|---|
| 不受上下文限制 | 状态可无限增长而成本不变 |
| **可检查** | 状态是结构化的，**程序可以直接读它判断进度与异常** |
| 可恢复 | 崩溃后从外部状态重建会话，而不是重放整段历史 |

第 2 条最容易被低估：**外部状态让"终止条件"和"失败检测"从模型判断变成程序判断。**

这比让模型自己说"我完成了"可靠得多——模型的自我报告会漏、会误报、会被上下文影响。

代价是**同步**：模型可能忘记更新外部状态。所以通常采用"**每步之后由代码强制更新**"，而不是"让模型自己报告"。

## 核心机制

- **常见形态**：待办清单（步骤 + 状态）、显式状态机（只允许合法转移）、数据库记录（任务进度、已处理条目）
- **同步方式**：**代码驱动**（每步后自动落盘，可靠）优于**模型驱动**（模型主动汇报，会漏）
- **与上下文的配合**：上下文里只保留**当前步骤**所需的信息与一份状态摘要，完整状态在外部
- **进度判定**：程序读外部状态判定完成与失败
- **与幂等性的关系**：外部状态记录"哪些已处理"，这是实现幂等重试的基础——没有它，重试无法判断该不该跳过
- **恢复**：新会话从外部状态重建上下文，只装载未完成的部分

## 边界：它不是什么

- **与[上下文管理](context-budget.md)的区别**：上下文管理在**窗口内腾挪**；外部状态把状态**移出窗口**。两者互补。
- **与数据库事务的区别**：这里不追求 ACID，而是保证 **Agent 的进度可追踪**。
- **与日志的区别**：日志是**事后记录**，外部状态是**当前事实**。查日志能知道发生了什么，但不能直接回答"现在还差哪几步"。

## 常见误解

1. **用上下文就够了** → 它会被压缩、被污染，且费用随长度增长。
2. **让模型自己汇报进度** → 会漏报误报，且模型对自己的状态并没有可靠的自省。
3. **外部状态只是优化** → 它是**可靠性的基础**：终止判定、失败检测、断点恢复都依赖它。
4. **状态存了就不用管** → 需要清理与归档策略，否则会累积成新的问题。

## 应用场景

- **该用**：多步任务、长任务、需要断点续跑、需要程序判定完成与失败
- **判断依据**：问一句——"**如果这次执行崩了，我能不能从某个地方恢复，而不是从头再来？**" 不能，就说明状态全在上下文里
- **配套**：[失败模式](failure-modes.md)中的目标漂移，很大一部分是靠外部状态来抑制的
