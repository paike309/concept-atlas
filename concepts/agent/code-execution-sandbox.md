## 一句话定义

**中文**：让模型生成并执行代码的环境，以及为控制其风险而设的一组隔离约束。

**English**: An environment where a model generates and runs code, together with the set of isolation constraints that bound the risk.

## 我的理解

代码执行把 Agent 的能力边界从"调用既定工具"扩大到"**自己造工具**"——这是质变。

同时它把风险从"用错工具"变成"**任意代码执行**"。风险等级完全不同。

所以它不是一个"更强大的工具"，而是**信任边界的移动**。设计时的核心问题不是"怎么跑代码"，而是"**跑不出问题来**"：

| 约束 | 要求 |
|---|---|
| 文件系统 | 只挂载必要目录，默认只读；写入限定在临时目录 |
| 网络 | **默认关闭**。开启则数据外泄与资源滥用成为首要风险 |
| 资源 | CPU、内存、时间、进程数**都要限** |
| 进程树 | 超时要杀**整棵**进程树，只杀父进程会留下孤儿 |
| 状态 | 每次执行用干净环境，避免残留影响与累积污染 |

一个常见误区是把"沙箱"当成一个开关。**它是一组约束的集合，漏掉任何一项都等于没有隔离。**

## 核心机制

**隔离级别**（从弱到强）：进程内执行（最危险）→ 子进程 + 资源限制 → 容器 → 更重的虚拟机或专用沙箱服务。

**关键约束清单**：文件系统挂载、网络出口、CPU/内存/时间配额、进程数上限、可用的系统调用。

**超时与进程树回收**：必须杀掉整个进程组，并确保子进程不会脱离进程组存活。

**工作目录清理**：每次执行使用独立临时目录并在结束后回收，否则磁盘会持续增长——这是长期运行系统里最常见的资源泄漏来源。

**输出限制**：截断超长输出。一次大量打印会撑爆上下文，比崩溃更隐蔽。

**该不该给网络**：绝大多数场景**不需要**。给了网络，前面所有隔离的意义都大幅下降。

## 边界：它不是什么

- **与[函数调用](function-calling.md)的区别**：函数调用是受控的既定接口；代码执行是开放环境。**不是同一种能力的强弱版本，而是两类不同的信任模型。**
- **与 REPL 的区别**：REPL 面向人交互，沙箱面向无人值守执行——后者的失败必须自动收敛。
- **与容器化部署的区别**：后者隔离的是**服务**；前者隔离的是**不受信代码**，威胁模型不同（有人主动尝试逃逸）。

## 常见误解

1. **容器就等于安全沙箱** → 默认配置下容器隔离性有限，共享内核、宽松的默认权限都是问题。
2. **设了超时就够了** → 不杀进程树会留下孤儿进程，长期累积。
3. **可以按需开放网络** → 网络一开，数据外泄成为首要风险。
4. **沙箱是运维的事** → 大部分约束来自**应用设计**（挂载什么、给什么凭据、输出限制）。

## 应用场景

- **该做**：数据分析、代码生成验证、需要动态计算的场景
- **判断依据**：列出三项——"这段代码**能访问什么**、**能持续多久**、**能占多少资源**"。三项里有一项说不清，就不该上线
- **配套**：与[权限与最小授权](least-privilege.md)配合——沙箱限制环境，最小权限限制能力

## 自测

1. 为什么说代码执行是"信任边界的移动"，而不只是更强大的工具？
2. 超时之外为什么还要显式杀进程树？不杀会发生什么？
3. 为什么说沙箱不是"一个开关"？漏掉哪一项最容易被忽视？
