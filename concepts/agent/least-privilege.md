## 一句话定义

**中文**：让 Agent 及其每个工具只持有完成当前任务所需的最小权限，并在必要时显式授权。

**English**: Granting an agent and each of its tools only the minimum permissions the task requires, with explicit authorization for anything beyond.

## 我的理解

这是 Agent 安全里**唯一真正有效的边界**。

理由是前面几层防御都是**概率性**的：提示注入防不住全部、越狱成功率不为零、模型会误判。而**权限是确定性的**——模型不能调用它没有的工具，不能访问它没有的凭据。

所以设计顺序应该是：

> **先按"最坏情况下模型被完全操控"来设计权限，再谈提示层防御。**

反过来做（先靠提示、出事再加限制）会在第一次事故时付出全部代价。

**权限最小化的三个维度**：

| 维度 | 做法 |
|---|---|
| 工具粒度 | 不给"执行任意 SQL"，给"按订单号查订单" |
| 数据范围 | 不给全库读权限，按租户/项目限定 |
| 时效 | 凭据短期有效、按需签发，不用长期万能 Key |

还有一条容易忽略的：**权限必须可撤销**。出问题时能否立刻切断，比事前防住多少更重要。

## 核心机制

- **工具设计层面**：参数应限制取值范围（订单号格式、日期区间上限），避免"万能参数"——万能参数把权限控制变成了提示词问题
- **凭据管理**：每个会话或任务使用独立凭据、短期有效；**不要把人的长期凭据交给 Agent**
- **环境隔离**：开发/测试/生产凭据分离，默认不接生产
- **高危操作清单**：任何不可逆操作（删除、付款、发消息、改权限）逐项列出，逐项决定是否需要人工确认
- **与[提示注入防御](prompt-injection-defense.md)的配合**：权限是底线，注入防御降低触发概率
- **审计**：记录每次工具调用及其参数，出事后能追溯影响范围

## 边界：它不是什么

- **与提示注入防御的区别**：一个是**确定性**边界，一个是**概率性**防御。必须叠加，不能互换。
- **与"访问控制"的区别**：传统访问控制面向**人**；这里面向 **Agent 这个新的行为主体**——它会犯错、会被操控、且行为不可完全预测。
- **与熔断/限流的区别**：后者限制**频率与总量**，前者限制**能做什么**。

## 常见误解

1. **模型足够可靠所以可以给宽权限** → 模型行为有概率性，且会被操控。
2. **只读权限就安全** → 读权限也可能造成批量数据外泄。
3. **权限问题上线后再收紧** → 收紧往往意味着改架构，成本远高于一开始就设计。
4. **有审批流程就不用最小权限** → 审批会被疲劳，且没法覆盖每一次调用。

## 应用场景

- **该做**：所有能触发有副作用动作的 Agent
- **判断依据**：问一句——"**这个 Agent 被完全操控时，最坏能造成什么损失？**" 如果答案是"不可逆的损害"，说明权限过大
- **不该做**：把权限控制托付给提示词或工具描述
