## 一句话定义

**中文**：给 Agent 及其工具发放访问外部系统所需的凭据，并保证这些凭据短期、最小、可撤销、且不进入模型上下文。

**English**: Issuing agents and their tools the credentials they need for external systems, kept short-lived, minimal, revocable, and out of the model's context.

## 我的理解

**Agent 凭据管理的特殊之处在于：要防的不只是外部攻击者，还要防"模型自己”。**

普通服务里凭据的威胁模型是"配置泄露"和"被入侵"。Agent 场景多两条：

1. **凭据可能进入上下文。** 只要某个工具的返回值、日志、错误信息里带了凭据，它就会进入模型上下文——而上下文会被**记录、压缩、摘要、甚至被模型复述出来**。**凭据一旦进了上下文，就等于进了不可控的存储。**
2. **模型可能被诱导去使用凭据。** 外部内容（网页、文档、工具返回）里夹带的指令，可以让 Agent 拿手上的凭据去访问本不该访问的地方。**这就是为什么凭据的作用域必须小到"即使被滥用也损失有限"。**

由此得到两条硬规则：

- **凭据归工具侧持有，不归模型侧。** 模型应当只看到"有一个可以执行某动作的工具"，而不是"这个工具的凭据是什么"。**凡是要把凭据放进提示词的设计，都是把权限交给了不可信输入。**
- **按任务发放、用完即废。** 长期凭据在 Agent 场景里尤其危险——它不是被使用一次，而是可能被无数次重放。

## 核心机制

**凭据的生命周期与要求**：

| 阶段 | 要求 |
|---|---|
| 生成 | 每个 Agent / 每个用途独立，不共用 |
| 发放 | **短期有效**（分钟到小时级），按任务下发 |
| 使用 | 仅在受控进程中（工具实现侧），不进入上下文与日志 |
| 轮换 | 定期且可强制（怀疑泄露时立即作废） |
| 撤销 | 能单独撤销某个 Agent / 某次任务的凭据 |

**三种常见做法**（按隔离强度递增）：

| 做法 | 说明 | 风险 |
|---|---|---|
| 长期密钥放在环境变量 | 简单 | 泄露后影响面大，无法按任务收敛 |
| 服务账号 + 短期令牌换取 | 每次任务换取临时凭据 | 换取服务本身的权限要严格限制 |
| 委托授权（代表用户） | 用用户的授权换取受限令牌，动作以用户身份发生 | 需要处理授权过期与范围收窄 |

**凭据最常泄露的四个地方**（按出现频率）：

1. **日志**（包括调试日志、异常堆栈、以及"为了方便排查"打印的请求信息）
2. **模型上下文**（工具返回、检索内容、以及被模型复述）
3. **错误信息回传给模型/用户**（上游服务把 token 放在错误详情里）
4. **版本库与镜像**（配置进了仓库、镜像层里有 .env）

**必须做的过滤**：对**所有进入上下文的内容**做凭据形态检测与脱敏——工具返回、检索片段、错误信息。**这是唯一能在"凭据已经出现"时兜住的一层。**

**与[函数调用](function-calling.md)的关系**：工具定义描述的是**能力**，凭据是**能力的许可**。两者要分开：模型选择"调用哪个工具"，运行时决定"这次调用有没有权限、用哪份凭据"。**把两者合并，等于让模型决定自己有多少权限**。

**审计要求**：每次凭据使用要有记录（谁、什么任务、访问了什么）。**Agent 场景下的审计不只是合规需要**——它是回答"这次异常访问是模型判断错误还是提示注入"的唯一依据。

## 边界：它不是什么

- **与[权限与最小授权](least-privilege.md)的区别**：那张卡定义**权限范围**（能做哪些动作），这张卡管理**凭据本身**（怎么发放、存放、撤销）。**授权范围再小，凭据管理不当也会被复用到范围之外。**
- **与[加密与密钥管理](../software/encryption-and-key-management.md)的区别**：那张卡讲密码学机制与密钥生命周期（加密数据用），这张讲 Agent 运行时**访问外部系统的凭据**。机制相同（都可能用到 KMS），但对象与威胁模型不同。
- **与[提示注入防御](prompt-injection-defense.md)的区别**：注入防御减少"模型被诱导"的概率，凭据管理限制"即使被诱导"的后果。**两者是概率与确定性的关系**——防御可能被绕过，作用域限制不会。
- **与"给 Agent 一个通用密钥"的区别**：通用密钥让 Agent 的所有动作共用一个身份，**无法区分正常调用与异常调用，也无法单独撤销**。

## 常见误解

1. **把凭据写进提示词让模型自己调用** → 等于把权限暴露给所有进入上下文的内容。
2. **凭据只在服务端就没问题** → 工具返回值、错误信息、日志都可能把它带回上下文。
3. **短期令牌麻烦，长期密钥更省事** → Agent 的调用频率与自主性让长期凭据的风险成倍放大。
4. **撤销不重要，反正会过期** → 出事时需要**立即**失效，过期时间通常远长于响应时间。
5. **审计只为了合规** → 它是区分"模型判断错误"与"被注入操纵"的唯一手段。

## 应用场景

- **该做**：任何让 Agent 访问外部系统（API、数据库、代码仓库、云资源）的场景
- **判断依据**：问四句——**凭据会不会进入上下文或日志**？**最短有效期是多久**？**能不能单独撤销一次任务**？**每次使用有没有记录**？
- **配套**：所有进入上下文的内容做脱敏；工具侧持有凭据；与[轨迹可观测性](trajectory-observability.md)关联（哪一次工具调用用了哪份凭据）
