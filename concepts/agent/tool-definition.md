## 一句话定义

**中文**：向模型描述一个可调用能力的三要素——名字、用途描述、参数模式（通常是 JSON Schema）。

**English**: The three-part description of a callable capability presented to a model — name, purpose description, and parameter schema (usually JSON Schema).

## 我的理解

工具是模型的手，但**模型看不见手，只看到一份说明书**。它对工具的全部认知都来自这段文字。

所以结论很直接：**说明书写得怎么样，直接决定工具用得对不对，这个权重不低于模型选择。**

一个常见错位：开发者按"代码接口"的思维写描述（参数名精确、措辞简短），但模型需要的是**"什么时候该用这个工具"的判断依据**。参数名精确只解决"怎么调"，不解决"该不该调"。

## 核心机制

**三要素**：

1. **名字** — 自解释、动作化。`search_orders` 优于 `query`，`create_refund` 优于 `process`。
2. **用途描述** — 说清做什么、什么时候该用、**什么时候不该用**。第三项最常被漏掉，但它是减少误调最有效的一句。
3. **参数模式** — 每个参数的类型、含义、**单位**、取值范围、是否必填。有枚举就给枚举，有默认值就写默认值。

**调用流程**：模型输出的不是函数调用本身，而是一段结构化文本（工具名 + 参数）。运行时解析、执行，把结果作为新消息回灌进上下文。

**返回值也是提示的一部分**——这一点常被忽略。返回值过长会挤占上下文；结构混乱会让模型误读；错误信息含糊会让它反复重试同一个错误。

## 边界：它不是什么

- **与 API 接口文档的区别**：API 文档写给程序员看。模型看得懂语法，但不知道"业务上什么时候该用"。工具描述必须额外回答业务判断问题。
- **与 [MCP](mcp.md) 的区别**：工具定义是**单个工具怎么描述**；MCP 是**工具怎么被发现与调用**（协议层）。一个是内容，一个是通道。
- **与 [提示工程](../ai/prompt-engineering.md) 的区别**：提示工程组织"这一轮的输入"，工具描述是"跨轮次稳定的能力清单"，属于配置而非临时输入。

## 常见误解

1. **参数名写清楚就够了** → 缺"什么时候该用"的判断依据，模型只能靠猜。
2. **工具越多越好** → 工具越多，选择歧义越大，误调率上升，同时描述本身占满上下文。应合并相关工具或分级暴露。
3. **返回值原样丢回去最保险** → 超长返回值会挤掉上下文并引入噪声。需要裁剪与结构化。
4. **错误信息随便写没关系** → 错误信息是模型修正策略的**唯一依据**。写 `error 500` 等于告诉它"再试一次同样的动作"。

## 应用场景

- **该做**：单个会话暴露的工具数量控制在可辨识范围内；返回值结构化且可裁剪；错误信息给出可执行的下一步
- **不该做**：把多个动作塞进一个工具用参数分支区分（模型难以判断选哪个分支）；让工具描述承担权限控制的责任
- **判断依据**：如果模型反复用错某个工具，**先改描述，再怀疑模型**

## 自测

1. 一个工具的用途只写了"查询订单"，模型可能怎么误用它？补哪一句话能有效减少误用？
2. 为什么工具返回值也需要设计？给出"返回值过长导致任务失败"的具体路径。
3. 把 30 个工具一次性全暴露给模型会遇到什么问题？有哪些缓解手段，各自的代价是什么？
