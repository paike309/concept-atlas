## 一句话定义

**中文**：把一个 Agent 任务花了多少钱算清楚，并把成本与任务成败挂上钩，而不是只看单次调用的单价。

**English**: Accounting for what an agent task actually costs, tied to task success rather than to per-call unit price.

## 我的理解

**Agent 的成本结构和普通 API 调用有一个本质差别：它随轮次超线性增长。**

原因在[上下文窗口](../ai/context-window.md)：**每一轮都要把之前的历史重新送进去**。所以第 n 轮的输入 ≈ 前面所有内容之和，总输入量随轮数近似**二次增长**——10 轮的对话不是 1 轮的 10 倍，而是远高于 10 倍。**这决定了"省成本"的主战场是控制轮数与上下文体积，而不是谈判单价。**

由此推出三条：

1. **有效指标是"单位任务成本"，不是"单位 token 成本"。** 单次便宜但成功率低的方案，重试与人工兜底会把总成本推高。**成本下降与成功率下降同时出现时，账面会变好看，实际更贵。**
2. **成本必须能归因到具体环节。** 总量没有意义：你需要知道是"检索塞了太多内容"、"工具返回太长"、还是"循环多跑了几轮"。**没有归因就没有优化的着力点**（与[容量规划](../software/capacity-planning.md)里"单位成本 + 归因"是同一套思路）。
3. **成本和延迟、质量是一个三角。** 加检索提升质量但增成本与延迟；降上下文省钱但可能降质量。**三者必须一起评估**，只看其中一项的优化通常只是把问题挪到了另两项。

## 核心机制

**成本构成**：

| 组成 | 特征 | 控制手段 |
|---|---|---|
| 输入 token | **随轮次累积增长**，通常是大头 | 压缩历史、控制检索条数、控制工具返回体积 |
| 输出 token | 每轮生成，含推理过程时更高 | 限制推理长度、结构化输出 |
| 工具调用 | 次数 × 单次成本（可能含外部计费） | 减少无效调用、缓存重复查询 |
| 失败重试 | **隐性成本大头**，最难统计 | 提高首次成功率、设置重试上限 |

**四种常见的成本浪费**（按隐蔽程度排序）：

1. **上下文里长期携带不再需要的内容**（已完成子任务的完整过程）
2. **工具返回的原始数据未裁剪**（整页 HTML、整个大对象）
3. **循环空转**（没有进展但仍在调用模型）
4. **重试未计数**（失败后重跑的成本被记在别处）

**必测的三个量**：

| 量 | 为什么 |
|---|---|
| 每任务平均轮数 | 轮数是二次增长的驱动因子 |
| 每任务输入 token 总量（含重试） | 真实成本主体 |
| 成功率 + 单位成功成本 | 把成本与质量绑在一起看 |

**多 Agent 场景的成本要格外小心**：多个分支各自消耗，总成本是**分支数之和**，且每个分支都有自己的上下文增长。**这就是"多 Agent 的成本通常是单 Agent 的数倍"的原因**——它必须由任务价值来正当化，而不是当成默认升级（见[多 Agent 通信与协调](multi-agent-coordination.md)）。

**压测与容量**：Agent 类系统的容量规划比普通服务更难，因为**单次请求的成本与时长方差极大**（同一个入口，简单任务与复杂任务可能差几十倍）。所以要按**分布**做容量评估（而不是平均值），并对超出正常分布的请求设置上限（见[终止条件与预算控制](termination-and-budget.md)）。

## 边界：它不是什么

- **与[终止条件与预算控制](termination-and-budget.md)的区别**：那张卡讲**怎么让循环停下来**（硬约束），这张讲**停下来之前花了多少、花在哪**（核算）。预算是闸门，核算是仪表。
- **与[上下文预算管理](context-budget.md)的区别**：上下文预算决定**每轮装多少**，成本核算决定**总量与归因**。前者是局部决策，后者是全局视角。
- **与"模型单价比较"的区别**：单价只是乘数之一，且往往不是最大项。**先看轮数与上下文体积，再谈单价**。
- **与[Agent 评测](agent-evaluation.md)的区别**：评测回答"行不行"，成本回答"值不值"。**两者必须一起看**：单独优化任何一个都会得出错误结论。

## 常见误解

1. **换个便宜的模型就能省一半** → 若成功率下降，重试与人工兜底会吃掉节省额。
2. **成本随轮数线性增长** → 上下文每轮重放，实际接近二次增长。
3. **总成本降了就是优化成功** → 要同时看成功率与单位成功成本。
4. **多 Agent 只是"多调几次"** → 各分支的上下文各自增长，总成本可能是数倍。
5. **失败重试的成本可以忽略** → 它常是隐性大头，且不在单次调用统计里。

## 应用场景

- **该做**：任何进入生产的 Agent 系统；上线前的成本估算；定价与配额设计（按任务而非按调用计费时尤其需要）
- **判断依据**：能回答三句——**每任务平均多少轮**？**输入 token 的构成里，检索/历史/工具返回各占多少**？**单位成功成本是多少**？
- **配套**：轮数与 token 归因进[可观测性](../software/observability.md)（按任务维度，不只是按调用维度）；成本异常纳入[告警](../software/alerting-and-on-call.md)；与[评测](agent-evaluation.md)联动，避免"降本降质"
