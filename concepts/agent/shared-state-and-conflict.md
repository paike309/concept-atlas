## 一句话定义

**中文**：多个 Agent 或多次运行共同读写同一份外部状态时，如何定义谁拥有它、写入冲突怎么办、以及最终以谁为准。

**English**: Defining who owns external state that several agents read and write, how write conflicts are resolved, and whose version wins.

## 我的理解

**共享状态的核心问题不是"怎么存"，而是"谁拥有它"。**

只要一份状态可以被多方写入，就必须回答三个问题，缺一个就会出现"数据看起来有，但没人能说清它为什么是这个值"：

1. **谁拥有它**（单一所有者，还是多方平等）
2. **冲突时以谁为准**（时间、优先级、还是人工）
3. **什么时候算收敛**（允许短暂不一致吗，收敛由谁触发）

这与软件工程里"冗余数据必须有权威源"的判断是同一个形状——**没有归属的共享状态，等价于没有权威源的冗余数据**（见[范式化与反范式化](../software/normalization.md)）。

由此推出两条：

- **优先设计成"单一写者"**。让每个状态片段只有一个写者（一个 Agent、或一个专门的写入阶段），其余只读。这消掉了绝大部分冲突，代价是写入方成为串行点——**但 Agent 场景的写入频率通常远低于读取，这个代价是可以接受的**。
- **并发写往往不是"真并发"，而是"顺序错"**。Agent 场景的冲突更多来自"两个步骤先后颠倒"（A 基于旧版本做了修改，B 也基于旧版本做了修改），因此**版本号 + 拒绝过期写入**比复杂的合并逻辑更实用。

## 核心机制

**三种状态归属结构**：

| 结构 | 做法 | 适合 | 代价 |
|---|---|---|---|
| 单一写者 | 只有一个 Agent/阶段能写 | 绝大多数场景的默认选择 | 该写者成为瓶颈 |
| 分区所有权 | 按字段/对象分区，各写各的 | 任务天然可切分 | 跨分区的一致性要单独处理 |
| 多方写入 + 合并 | 都写，冲突按规则合并 | 对等协作、需要多视角 | **合并规则本身要设计，且难以验证** |

**冲突解决的常见规则**（按可靠性从高到低）：

| 规则 | 说明 | 问题 |
|---|---|---|
| 拒绝过期写入 | 携带版本号，不匹配即拒绝 | 需要调用方处理失败 |
| 单一所有者裁决 | 归属方写入，其它方只提交建议 | 需要一次额外的决策步骤 |
| 按优先级覆盖 | 高优先级写者覆盖低优先级 | 低优先级的信息会丢失 |
| 最后写入获胜 | 简单 | **静默丢更新**，在 Agent 场景尤其危险 |

**"最后写入获胜"为什么在 Agent 场景更危险**：Agent 的写入通常是**有语义的修改**（"把状态改成已完成"、"把预算减去已用"），不是幂等的赋值。**静默覆盖等于悄悄丢掉了另一个分支的工作**，而且不留痕迹——排查时只能看到"某次运行后状态不对"。

**必须记录的东西**（否则冲突无法排查）：

- **写入者标识**与**时间**（谁在什么时候改的）
- **版本或前后值**（能回答"这次改动基于哪一版"）
- **变更原因**（Agent 的哪一步决策导致的）——这条把状态变更与[轨迹](trajectory-observability.md)关联起来，是唯一能解释"为什么状态变成这样"的方式

**收敛的定义**：允许不一致时，必须说明**不一致窗口**与**收敛触发条件**（谁在什么时候把状态对齐）。**没有收敛机制的多方写入，最终会稳定在一个谁也无法预测的状态上**——而它看起来完全正常。

**常见的状态划分**（按"要不要共享"重新审视）：

| 类型 | 是否该共享 |
|---|---|
| 任务进度、待办列表 | 应该共享（多方都需要读） |
| 中间推理过程、草稿 | **通常不该共享**（只属于某个 Agent，共享只会污染上下文） |
| 长期事实、用户偏好 | 应该外置并单一所有者 |
| 缓存类中间结果 | 可以共享，但要允许丢弃与重建 |

**一半以上的"共享状态问题"可以通过"不共享"解决**——先问"这个字段真的需要被多方读到吗"。

## 边界：它不是什么

- **与[结构化状态与外部存储](structured-state.md)的区别**：那张卡讲**为什么**把状态移出上下文（避免上下文膨胀与丢失），以及移到哪里；这张卡讲**移出去之后多方访问怎么不乱**。前者解决"记不住"，后者解决"记乱了"。
- **与[上下文预算管理](context-budget.md)的区别**：预算管理决定**每个 Agent 能看到多少**，共享状态决定**大家看到的是不是同一份**。**可见量不等于一致**。
- **与数据库事务的区别**：Agent 的"写入"通常是自然语言决策的产物，**没有明确的边界与回滚语义**。数据库事务能保证原子性，但它保证的不是"这个决定该不该做"。
- **与[长期记忆](long-term-memory.md)的区别**：长期记忆是**跨会话的检索型存储**，共享状态是**当前任务的权威记录**。把两者混用会导致"任务状态里塞满了历史偏好"这类污染。

## 常见误解

1. **状态存进数据库就一致了** → 存储解决持久化，不解决谁拥有与谁覆盖谁。
2. **最后写入获胜够用** → 它静默丢更新，且在有语义的修改上后果更严重。
3. **让所有 Agent 都能写更灵活** → 灵活性换来的是不可解释的状态演化。
4. **共享越多协作越好** → 中间推理与草稿共享只会污染彼此的上下文。
5. **状态不一致会自己收敛** → 没有收敛机制时，它会稳定在一个错误但自洽的状态上。

## 应用场景

- **该做**：多个 Agent 或多次运行需要读写同一份任务状态的系统
- **判断依据**：对每个共享字段问四句——**谁拥有它**？**别人写它时怎么处理冲突**？**写入能不能追溯到某一步决策**？**允许不一致吗，谁负责收敛**？
- **配套**：状态变更与[轨迹](trajectory-observability.md)关联；版本号 + 拒绝过期写入；把"不需要共享的字段"从共享状态里移出去
