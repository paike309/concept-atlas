## 一句话定义

**中文**：让 Agent 循环在有限步数、时间与成本内停止的外部强制机制。

**English**: Externally enforced mechanisms that guarantee an agent loop terminates within bounded steps, time, and cost.

## 我的理解

**模型不会自己停。** 这不是能力问题，是机制问题。

它每次前向做的只有一件事：根据当前上下文生成最可能的下一步。而"任务已经完成了"这个判断，在它眼里和"再调一次工具"没有本质区别——两者都是"下一个 token"。

所以终止必须**由外部强制**，而且必须是硬约束（计数、超时、预算），不能是提示词里的请求。**"完成任务后请停止"是一条建议，不是约束。**

另一个常被忽略的点：**终止条件要和任务预算匹配**。给一个 30 秒预算的任务配 100 步上限，等于没有上限——它会把预算先花完。

## 核心机制

四类必须设的终止条件：

| 类型 | 作用 | 漏掉的后果 |
|---|---|---|
| 成功终止 | 模型给出最终答案，不再请求工具 | — |
| 步数上限 | 循环轮次上限 | 绕圈时无限消耗 |
| 单步超时 | 任何一次工具调用都有超时 | 工具挂住时整个循环一起挂住 |
| 总预算 | 累计 token / 金额上限 | 真正兜底的那一条，成本失控 |

另外两类需要单独处理：

- **人工中断**：用户主动停止。面向用户的同步请求必须支持
- **异常终止**：工具连续报错、达到重试上限

**实现位置很关键**：这些检查必须在**循环控制层**，不能在工具内部。工具只能发现自己这一层的问题，看不到"整体在绕圈"或"已经花了多少钱"。

**与重试的配合**：重试是在失败后重来，终止是停止。两者配合使用——重试 N 次仍失败 → 终止并上报。**无上限的重试本身就是新的死循环。**

## 边界：它不是什么

- **与提示词里"请尽快完成"的区别**：那是请求，可以被忽略；计数与超时是机制，不能。把安全机制寄托在提示词里，等于没有机制。
- **与循环检测的区别**：循环检测发现"在做重复的事"（内容层面），是优化；终止条件保证"一定会停"（机制层面），是底线。前者不能替代后者，因为循环检测本身也可能失效。
- **与限流的区别**：限流控制进入的请求量，终止控制单个任务的生命周期。两者维度不同。

## 常见误解

1. **模型足够强就不会无限循环** → 循环的成因常常是工具返回内容无变化、或错误信息被忽略，与模型强弱关系有限。
2. **设个步数上限就够了** → 单次工具调用可能挂住很久，必须同时有单步超时。
3. **超时了重试就行** → 无上限的重试是新的死循环。
4. **预算是运维的事** → 预算是设计参数，它决定循环结构长什么样。事后加预算通常要改架构。

## 应用场景

- **必须设**：任何无人值守的循环；任何会调用外部服务的循环；任何有外部副作用的操作（下单、发消息、改文件）
- **不能放松**：面向用户的同步请求（必须能被中断）
- **判断依据**：写下"最坏情况下这个任务会花多少步、多少时间、多少钱"。**如果有任何一项写不出具体数字，就等于没有预算。**
