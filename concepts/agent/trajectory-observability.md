## 一句话定义

**中文**：记录 Agent 每一步的输入、决策、动作与返回，使整条执行路径可检查、可回演、可归因。

**English**: Recording every step of an agent's input, decision, action, and result so the execution path is inspectable, replayable, and attributable.

## 我的理解

**Agent 的输出是一条轨迹，不是一次回答。**

这个差别决定了一切。单次回答出错，看输入输出就够了；轨迹出错，你必须知道**是哪一步开始偏的**。而由于 Agent 是非确定性的，"复现"本身都成问题。

所以轨迹记录不是可观测性的加分项，**它是调试的前提条件**。

第二条同样重要：记录的目的是**归因**，不是日志堆积。写下"第几步、看到了什么、选了什么、为什么失败"，比存下十兆原始文本有用得多。

## 核心机制

**每一步应落盘的最小集合**：

| 字段 | 说明 |
|---|---|
| 序号与时间戳 | 定位与耗时分析 |
| 上下文摘要 | token 占用、本轮裁掉了什么。**不是全文** |
| 模型决策原文 | 含工具名与参数 |
| 工具执行结果 | 或错误信息，含耗时 |
| 终止原因 | 成功 / 步数 / 超时 / 预算 / 人工 |

**两个回放层次**：

- **重放（replay）**：用相同上下文重跑模型，观察是否复现。需要固定采样参数（温度等），成本高且不保证一致
- **回演（re-enact）**：不调模型，直接按记录展示路径。**永远可行、成本为零**，是日常定位的主力

**失败现场保留**：把失败案例的完整轨迹单独存档，逐渐形成回归集——这是 Agent 版本的测试用例库。它把"偶发问题"变成"可重复检验的问题"。

## 边界：它不是什么

- **与普通日志的区别**：日志回答"发生了什么"，轨迹回答"**为什么走了这条路**"。轨迹必须有结构、可逐步查询，不能是纯文本流。
- **与指标的区别**：指标（成功率、平均步数）告诉你**有没有**问题，轨迹告诉你问题**在哪**。两者互补，不可替代。
- **与提示词调试的区别**：提示词调试看单次输入，轨迹看**序列**。很多 Agent 问题只存在于序列层面——第三步的小错误在第五步被放大。

## 常见误解

1. **出错了看最后一步就行** → 偏差常发生在更早的步骤，只是到后面才显形。看最后一步通常只能看到"症状"。
2. **记全量原文最保险** → 全量原文既贵又难查。**没有结构就没有可查询性**，等于没记。
3. **Agent 是随机的，没法复现** → 完全复现困难，但结构化回演加失败存档足以定位大部分问题。
4. **这是上线后再说的事** → 没有轨迹，开发阶段就无法定位问题。它属于开发工具，不属于运维。

## 应用场景

- **该做**：任何多步 Agent；任何有外部副作用的调用（下单、发消息、改文件）；任何需要向用户解释"为什么这么做"的场合
- **判断依据**：问一句——**"如果这个任务明天失败了，我能指出是哪一步、为什么吗？"** 答不出来，就说明缺轨迹
- **配套**：[上下文预算管理](context-budget.md)的每轮占用分布应当落在轨迹里，否则"上下文爆了"这件事无法被事后发现
