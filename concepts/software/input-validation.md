## 一句话定义

**中文**：对所有来自信任边界之外的数据，在其进入可信区域之前做校验与规范化。

**English**: Validating and normalizing all data crossing into the trusted region before it is used.

## 我的理解

**输入校验的本质是信任边界问题：哪些数据可信、跨过哪一行之后才可信。** 没有边界定义，就没有校验标准——这也是为什么"校验做没做全"经常争论不清。

最常见的漏洞不是"忘了校验长度"，而是**边界划错**：只把用户表单当外部，忘了 HTTP 头、URL 参数、文件内容、消息队列里的消息，以及**上游服务的返回值**。最后一条尤其反直觉：**上游的响应对你而言是不可信输入**——它可能被上游的漏洞、错误配置或被篡改的中间环节污染。

由此得到三条原则：

1. **白名单优先。** 定义"什么是对的"，而不是枚举"什么是错的"。黑名单永远漏——攻击者只需要找到一个你没列出的变体。
2. **校验在进入时做一次，之后靠类型。** 如果同一个字段在十个地方被重复校验，说明数据没有"已验证"这道关；这是设计问题，不是勤奋。
3. **校验失败应当显式拒绝，而不是"尽量清洗后继续"。** 清洗会掩盖上游错误，也让攻击面难以推理。例外是需要保留用户内容的场景（如富文本），此时用成熟的净化库并严格按其规则处理。

还有一条必须记住的区分：**校验 ≠ 编码。** 校验控制"能不能进来"，编码控制"进来之后会不会被当成代码执行"。**SQL 注入与 XSS 的根治手段是参数化查询与输出编码，不是输入过滤。**

## 核心机制

**校验的四个层面**：

| 层面 | 内容 | 漏掉的后果 |
|---|---|---|
| 语法 | 类型、格式、长度、范围 | 解析异常、越界、类型混淆 |
| 语义 | 业务合法性（如"结束时间晚于开始时间"） | 状态不一致 |
| 规范化 | 统一编码与 Unicode 形式 | 绕过校验（同一内容多种表示） |
| 上下文输出编码 | 按输出去向分别编码 | 注入类漏洞 |

**根治手段与它们各自解决什么**：

| 手段 | 根治的问题 | 说明 |
|---|---|---|
| 参数化查询 / 预编译 | SQL 注入 | **把结构与数据分离**，不做"过滤"也能根治 |
| 输出编码（按上下文） | XSS | 输出到 HTML / JS 字符串 / URL / CSS 各用各的规则 |
| 白名单校验 | 非法取值的业务问题 | 例如排序字段必须是已知列名之一 |

**常见绕过来源**（也是"为什么黑名单不行"的答案）：Unicode 规范化差异、双重编码、大小写与全半角变体、空字节、超长输入、类型混淆（JSON 里数字与字符串混用）、以及**上下文切换**（同一段数据先进入数据库，再被输出到 HTML）。

**文件上传是特殊一类**：扩展名、魔数（文件头）、内容扫描、存储位置（不要放在可直接访问的路径）、是否可执行——每一层都要管，只查一层必然被绕过。

## 边界：它不是什么

- **与[契约设计](contract-design.md)的区别**：契约描述**接口承诺**（调用方可以依赖什么），校验是**运行时的防守动作**。契约清楚会让校验更简单，但契约是文档加测试，**不替代运行时校验**——攻击者不遵守契约。
- **与输出编码的区别**：这是最容易被混淆的一对。校验管入口，编码管出口。**只做入口过滤的 XSS 防护一定会被绕过**；只做出口编码的系统，也需要入口校验来处理业务合法性问题。
- **与[参数化查询](contract-design.md)的关系**：参数化是结构性手段，它不"过滤"输入但彻底消除 SQL 注入。**输入校验不能替代它**——两者解决的不是同一层问题。
- **与[提示注入防御](../agent/prompt-injection-defense.md)的区别**：那是同一思路在 LLM 场景下的形态（外部文本可能被模型当作指令）。**传统输入校验无法覆盖提示注入**——不存在"把自然语言里的指令过滤掉"的白名单方案。

## 常见误解

1. **前端校验过就够了** → 前端可被完全绕过，它只是体验优化。
2. **用了 ORM 就没有注入** → 拼接字符串、动态表名与排序字段仍是常见漏洞点。
3. **黑名单过滤关键词能防注入 / XSS** → 编码变体与上下文切换会绕过。
4. **内部服务可以信任** → "内网默认可信"正是横向移动的起点。
5. **校验了长度就够** → 类型、范围、语义、规范化、输出上下文都要管。
6. **清洗（sanitize）比拒绝更友好** → 它把攻击面变成不可推理的状态。**拒绝是更安全的默认。**

## 应用场景

- **该做**：所有跨越信任边界的数据，包括用户输入、上游服务响应、消息队列消息、文件内容、**环境变量与 DNS 结果**
- **判断依据**：画一条线——**哪些数据来自你的进程之外**。这条线上每一个入口都要有校验，且校验失败要显式拒绝
- **配套**：按上下文做输出编码、用参数化查询、错误信息不回显内部细节（否则错误信息本身就是信息泄露）
