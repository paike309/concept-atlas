## 一句话定义

**中文**：通过加锁把并发执行的多个操作在时间上或逻辑上排开，使"检查—修改"这类复合动作不再互相穿透。

**English**: Ordering concurrent operations through locking so that compound actions — check-then-act — cannot interleave destructively.

## 我的理解

**锁的失败很少是"忘了加锁"，多半是粒度与持有时间的问题。**

两种典型失衡：

- **锁太粗**：把无关操作也串行化，吞吐被压死。表现是"并发数上去了但吞吐不涨"。
- **锁太细 / 加错位置**：把本该原子的复合动作拆成了两次加锁——`读 → 判断 → 写` 三步之间，状态已经被别人改掉了。**这就是 check-then-act 陷阱，是并发 bug 的第一大来源。**

由此得到一条判断：**判断某段代码需要不需要锁，标准是"它有没有依赖于之前读到的状态"**，而不是"它有没有写共享变量"。

第二条：**锁是有层级与作用域的**。进程内的锁挡不住另一个进程；数据库的行锁挡不住你在应用层先读出来的旧值。**最常见的混合错误是"在应用层判断、在数据库层写入"**——两者之间没有任何锁保护。

第三条（成本视角）：**乐观与悲观不是风格之争，而是冲突概率之争**。冲突极少时，版本号 + 失败重试（乐观）比全程加锁吞吐更高；冲突频繁时，乐观方案会陷入重试风暴，此时悲观锁更稳。

## 核心机制

**锁的几种维度**：

| 维度 | 取值 | 说明 |
|---|---|---|
| 粒度 | 行 / 页 / 表 / 全局 | 粒度越粗，并发越低 |
| 模式 | 共享（读）/ 排他（写） | 读读相容，读写与写写互斥 |
| 策略 | 乐观 / 悲观 | 按冲突概率选 |
| 范围 | 进程内 / 跨进程 / 数据库 | **不同范围的锁互不生效** |

**死锁的四个必要条件**（打破任一即可预防）：互斥、持有并等待、不可抢占、循环等待。工程上最好用的是**统一加锁顺序**——所有代码按同一顺序获取多把锁，循环等待就不成立。

**死锁的处理方式两种**：

- 预防：统一顺序、一次性获取、设置超时
- 检测并回滚：数据库通常这么做（牺牲一个事务），因此**应用必须能处理"被选为牺牲者"的失败并重试**（见[隔离级别与并发异常](transaction-isolation.md)）

**乐观并发的实现**：版本号或时间戳。更新时带上读到的版本，`WHERE version = ?` 命中 0 行即表示"期间被别人改过"，此时重试或报冲突。**它把冲突检测从"加锁"变成了"更新失败"**——代价是必须处理失败路径。

**锁与事务的配合**：`SELECT ... FOR UPDATE` 之类是在事务内显式加锁，用来保护"读—判断—写"。它的前提是**整个动作在一个事务里**，否则锁在事务结束时就释放了，保护不了后续步骤。

**必须观测的指标**：锁等待时间、死锁次数、重试次数。**重试次数的上升是乐观并发失控的早期信号**（它常先表现为延迟上升，而不是错误率上升）。

## 边界：它不是什么

- **与[隔离级别](transaction-isolation.md)的区别**：隔离级别是**数据库提供的可见性规则**，锁是**实现控制的手段**（手动加锁是绕过隔离级别不足的办法）。两者一个是对外承诺，一个是内部机制。
- **与[幂等性](idempotency.md)的区别**：锁防的是**并发同时发生**，幂等防的是**同一个操作被执行多次**。**两者不可互替**：串行执行同一操作两次，锁一点忙都帮不上。
- **与[竞态与内存模型](memory-model-and-races.md)的区别**：那张卡讲的是**没有同步时读写可见性与重排**的问题（更底层，常出现在无锁代码里）；这张卡讲的是**用锁建立互斥**。前者问"这个写什么时候能被看见"，后者问"这两个操作能不能同时发生"。
- **与队列的区别**：队列把并发改写为串行处理（如单线程消费），是一种**从设计上消除锁**的手段。当业务允许异步化时，它比调锁更省心。

## 常见误解

1. **加锁就一定安全** → check-then-act 中间解锁、锁范围与共享数据不匹配，都是加了锁仍出问题。
2. **测试通过就说明没有并发问题** → 竞态依赖时序，测试环境通常负载低、路径少，**通过只说明这次没触发**。
3. **锁越细性能越好** → 每次加解锁都是成本，且细粒度会引入更多死锁可能。
4. **读操作不需要锁** → 取决于是否需要"读到一致的一组数据"；先读后判断的场景仍需要。
5. **乐观锁不需要处理失败** → 冲突时更新会失败，不处理就等于静默丢更新。
6. **应用层能判断的事情不用锁** → 判断与使用之间没有保护，正是竞态窗口。

## 应用场景

- **该用悲观锁**：冲突频繁、重试代价高（如扣减库存、账务）、逻辑复杂的临界区
- **该用乐观并发**：冲突概率低、重试成本低、读多写少
- **该避免锁**：能用队列/单写者串行化时，优先从设计上消除并发
- **判断依据**：问三句——**这段代码是否依赖之前读到的状态**？**它和谁共享数据，锁的范围覆盖到了吗**？**冲突概率与重试成本哪边更低**？
- **配套**：锁等待与死锁次数进[可观测性](observability.md)；被选中作为死锁牺牲者的事务必须能重试，因此写操作要[幂等](idempotency.md)
