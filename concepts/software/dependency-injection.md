## 一句话定义

**中文**：一个对象所需要的协作者由外部传入，而不是由自己在内部构造——把"用谁"的决定权从被使用者手里交给调用方。

**English**: A pattern in which an object receives its collaborators from the outside instead of constructing them itself, moving the decision of "which implementation" to the caller.

## 我的理解

关键在**决定权搬家**。

不用 DI 时，`OrderService` 自己 `new SqlOrderRepo()`，于是"订单怎么存"这件事被焊死在这个类里。想换成内存实现做测试，只能改这个类的代码。

用 DI 时，外部把 repo 传进来。`OrderService` 只知道"有个东西能存取订单"，不知道具体是什么。替换实现不用碰它。

所以 DI 的真实收益是**把变化点从内部推到边界**。它不是"为了测试"，测试只是这个收益最容易观察到的表现。同理，把 DI 和 DI 容器划等号也是错的——手写构造函数传参就是 DI，容器只是自动化了"谁来传"这件事，而且往往引入新问题（见「边界」）。

## 核心机制

**三种注入方式**：

| 方式 | 形式 | 适用 |
|---|---|---|
| 构造器注入 | 构造时传入，存为不可变字段 | 必需依赖。缺了就构造不出来，编译期/启动期即暴露 |
| 属性注入 | 构造后赋值 | 可选依赖、框架托管对象 |
| 方法注入 | 每次调用时传入 | 依赖随调用变化，如传入不同的事务或租户上下文 |

**优先构造器注入**。理由是显式：看构造函数签名就知道这个类依赖什么，依赖列表无法被隐藏，也不会出现"对象造出来了但还没可用"的中间态。

**容器做什么**：读取配置（或扫描注解）建立"接口 → 实现"的映射，按依赖图递归构造对象，并管理生命周期（单例 / 请求级 / 瞬时）。它的价值在对象图很深时体现——手写装配几十层的对象树确实痛苦。

**依赖图的方向**：依赖应指向抽象（接口），实现类在装配层被绑定。这样业务代码不依赖具体技术选型。

## 边界：它不是什么

- **DI 与 IoC 的区别**：IoC 是更上位的原则——"控制权从你的代码交给框架"。DI 是 IoC 在"对象依赖"这一件事上的具体做法。事件回调、模板方法也是 IoC。所以 "IoC 容器" 这个叫法比 "DI 容器" 更宽，但业界常混用。
- **DI 与 DI 容器的区别**：DI 是模式，容器是工具。**不用容器也能完整实现 DI**，而且在库代码、小项目里通常应该不用。
- **与服务定位器（Service Locator）的区别**：服务定位器也是"从外部拿依赖"，但依赖是对象**主动去问容器要**的（`container.get(X)`）。区别在于依赖关系不再出现在构造函数签名里——隐藏了依赖，是 DI 想解决的问题反过来了。

## 常见误解

1. **DI 必须用框架** → 构造函数传参就是 DI。把容器引入小项目，换来的是启动期错误取代编译期错误、调用链难以静态追踪、调试时要先理解容器行为。
2. **DI 只是为了写单元测试** → 测试只是附带好处。主要收益是替换实现（多存储后端、多支付渠道）和把依赖方向倒置。
3. **注入的依赖越多越好** → 构造函数有 8 个参数通常不是 DI 的功劳，是**这个类承担了太多职责**的信号。DI 会诚实地把这个问题暴露出来，不要用属性注入去掩盖它。
4. **容器管理的生命周期是细节** → 单例持有请求级对象（captive dependency）是最常见的一类生产事故：数据跨请求泄漏。生命周期不是配置问题，是正确性问题。

## 应用场景

- **该用**：实现会在运行时或部署时替换（多数据源、多外部服务）、需要隔离外部副作用以便测试、依赖需要跨调用共享（连接池、缓存）。
- **不必用**：依赖固定且不涉及外部资源的小工具类、纯粹的数据结构与算法代码。给它套一层接口只是增加间接层。
- **判断依据**：问"这个依赖**现在**有没有第二种实现，或者**预计**会不会有"。两个都是否，就不值得抽象。
- **替代方案**：语言层面已有更好工具时优先用——参数传递、函数式组合、模块系统本身就够。DI 在静态类型 + 大团队 + 长生命周期的代码库里收益最大。
