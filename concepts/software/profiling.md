## 一句话定义

**中文**：用采样的方式测出程序时间实际花在哪里，从而把"哪里慢"从猜测变成测量。

**English**: Measuring, by sampling, where a program actually spends its time — turning "what is slow" from a guess into a measurement.

## 我的理解

**性能问题上，直觉的准确率极低，所以纪律只有一条：先测量，再优化。**

直觉失效的原因很具体：**人根据代码结构推测热点，而热点由数据分布与运行路径决定。** 一段看起来复杂的代码可能一次都不执行；一段三行的循环可能是全部时间所在。所以结论往往反直觉：

- 优化"看起来慢"的地方，通常不会改善整体
- **优化非瓶颈部分，收益上限由 Amdahl 定律封死**：如果那段只占 10% 的时间，哪怕优化到零，总提升也不超过 10%

第二条：**剖析本身是一种观测，会改变被观测对象**。采样有开销、插桩开销更大、日志会改变时序。所以：**优先用低开销的采样方式**，且要意识到"剖析下变慢"不等于"生产也这么慢"。

第三条：**剖析有两种用途，别混**。一种是"找出瓶颈在哪"（采样剖析、火焰图），另一种是"验证改完有没有变快"（基准测试）。**前者要全局视野，后者要可重复的固定条件**——用同一个工具硬套两个目的，通常两边都不准。

## 核心机制

**剖析的几种类型与各自能回答的问题**：

| 类型 | 回答 | 开销 |
|---|---|---|
| CPU 采样 | 时间花在哪些函数/调用栈 | 低 |
| 内存/分配剖析 | 分配热点、内存增长来源 | 中 |
| IO 剖析 | 磁盘/网络等待占比 | 低 |
| 锁竞争剖析 | 等待锁的时间（**不占用 CPU 的等待**） | 中 |
| 追踪/插桩 | 精确调用次数与耗时 | 高 |

**一个关键区分：CPU 剖析看不到"等待"。** 如果程序大部分时间在等数据库、等网络、等锁，CPU 剖析会显示"CPU 使用率不高"，让你误判为"性能没问题"——**实际上瓶颈在别处**。这类问题要看延迟分布与等待时间，而不是 CPU 花在哪。

**火焰图的读法**：

- 横轴是**时间占比**（不是调用顺序，也不是调用次数）
- 纵向是调用栈，越深越靠近叶子
- **找"宽"的帧，而不是"深"的帧**——宽度才是成本
- 没有叶子的宽帧往往是"卡在系统调用里"（等待 IO）

**采样的统计性质**：采样数量越少，噪声越大。短时间的剖析可能把噪声当成热点，所以**要采够样本，或把同一负载重复几次取稳定模式**。

**基准测试的三条纪律**：固定条件（同一份数据、同一台机器、同一版本依赖）、重复多次取分布（不是取最好的一次）、**测真实负载路径**（微基准里的调用与生产路径不同，常量折叠与缓存效应会让结果失真）。

## 边界：它不是什么

- **与[可观测性](observability.md)的区别**：可观测性面向**生产运行中的系统**（低开销、持续、回答"为什么这次慢"）；剖析面向**开发与排查时的深入分析**（开销更高、可回答"时间花在哪一行"）。**两者互补，不可互替**：可观测性发现异常，剖析定位到代码。
- **与[查询计划](index-and-query-plan.md)的区别**：查询计划是**数据库内部的执行策略**，剖型是**应用侧的时间分布**。一个慢请求可能 90% 时间在数据库，此时应用侧剖析只显示"等待"——**要顺着这个线索去看计划，而不是去优化应用代码**。
- **与[容量规划](capacity-planning.md)的区别**：剖析解决"同样的负载怎么更快"，容量规划解决"能撑多少负载"。前者是效率问题，后者是能力问题。**负载会持续增长时，先分清是该提效还是该扩容。**
- **与"加缓存"的区别**：缓存是**绕过**开销，剖析是**消除**开销。绕过更快见效，代价是引入一致性问题（见[缓存策略](caching-strategies.md)）。

## 常见误解

1. **凭经验就能找到热点** → 热点由数据与路径决定，与代码观感无关。
2. **优化任何部分都能提升整体** → Amdahl 定律：非瓶颈部分优化收益有上限。
3. **CPU 使用率不高就说明性能没问题** → 瓶颈可能在等待（IO、锁、下游）。
4. **剖析没开销** → 采样开销低但非零，插桩开销很高。
5. **基准测一次就够** → 单次结果包含大量噪声，需要重复并看分布。
6. **优化完不需要复测** → 改动的收益必须被验证，否则你不知道自己是否真的改对了地方。

## 应用场景

- **该做**：优化之前（确定目标）、优化之后（验证收益）、以及容量决策之前（判断瓶颈是效率还是能力）
- **判断依据**：先回答两个前置问题——**这是延迟问题还是吞吐问题**？**时间花在计算上还是等待上**？答错方向，后面所有优化都是白做
- **配套**：生产侧用[可观测性](observability.md)发现异常并保留上下文，开发侧用剖析深入；剖析结论要能写进[技术债](technical-debt-refactoring.md)记录（避免同一处被反复"优化"）

## 自测

1. 为什么"优化非瓶颈部分"的收益有上限？这个上限怎么估？
2. CPU 使用率不高但请求很慢，最可能是什么类型的问题？该用什么工具？
3. 火焰图里为什么要找"宽"的帧而不是"深"的帧？
