## 一句话定义

**中文**：事故中优先恢复服务、事故后无责地还原真相，并把结论变成有主有期的改进项。

**English**: Restoring service first during an incident, then reconstructing what happened without blame, and turning the findings into owned, dated action items.

## 我的理解

**事故中与事故后的目标必须分开，混在一起是延长故障的主要原因。**

- **事故中：止血优先，不是找根因。** 用户正在受损时，"为什么会这样"是次要问题；"怎么能先恢复"才是首要问题。很多事故被拖长，是因为团队在故障期间坚持要搞清楚原因才肯动手回滚。
- **事故后：找根因，而且要找全。** 这时候时间充裕，目标是让同类问题不再发生。

由此推出两条：

1. **缓解手段有优先级**：**回滚 > 限流/降级 > 修复**。回滚是最快且最确定的手段（这正是[部署与发布策略](deployment-strategies.md)要求"回滚路径必须事先验证"的原因）；改代码修复最慢，且在高压力下容易引入新问题。**先恢复，再修**。
2. **复盘必须无责，否则信息会消失。** 有责复盘得到的是"可被追责的那部分叙述"，而不是真相——人人都会先想"这会算到谁头上"。**而真相恰恰藏在那些"我本来应该注意到但没注意到"的细节里**，这些细节只有在不追责时才有人愿意说。

复盘的产出**不是一份报告，而是可执行的改进项**。没有 owner 与期限的改进项就是许愿。**判定一次复盘是否有效，看三个月后那些改进项的状态，而不是看报告写得多完整。**

## 核心机制

**事故中的三个角色**（人数少时可以兼任，但职责必须有人担）：

| 角色 | 负责 | 不负责 |
|---|---|---|
| 指挥 | 决策与分工、维持节奏 | 亲自排查 |
| 沟通 | 对外（用户/内部）同步状态 | 技术决策 |
| 执行 | 动手处理 | 对外发布信息 |

**为什么要显式分角色**：事故中最大的浪费是**多个人同时做同一件事、或者都在等人做决定**。指定指挥是最便宜的改进——它把"谁来定"这个问题从现场移除。

**处置顺序**：

1. **评估影响范围**（哪些用户、哪些功能）——它同时决定对外沟通的内容与优先级
2. **抑制扩散**（限流、摘除故障节点、关闭相关开关）
3. **尝试最快恢复**（回滚优先）
4. **记录时间线**——**在处置过程中记，不是事后凭记忆补**。时间线是复盘唯一的原始材料，事后回忆会系统性地把事件压缩成一条更合理的因果链（这正好抹掉了最有价值的部分）

**复盘的内容要求**：

| 部分 | 要点 |
|---|---|
| 时间线 | 发现、升级、缓解、恢复各自的时间点 |
| 影响 | 用户可感知的范围与持续时长（不是内部指标） |
| 根因 | 多因时并列，**不强行收敛到单一"根本原因"** |
| 触发条件与放大因素 | 为什么小问题变成了大事故（通常是缺失的防护） |
| 改进项 | 每条有 owner、期限、验收方式 |

**"根因只有一个"是一个需要警惕的说法。** 现代故障几乎都是**多因链**：一个触发条件 + 若干防护缺失。强行归因到单点，会让人只修那一处，而真正放大事故的缺失防护仍在原处。

**改进项的分类**（优先级通常从高到低）：**检测能力**（下次更早发现）→ **缓解能力**（下次更快恢复）→ **预防**（不让它发生）。原因是：**你无法预防还没想到的事故，但可以普遍提升检测与缓解能力**——这两项对未知故障同样有效。

## 边界：它不是什么

- **与[告警与值班](alerting-and-on-call.md)的区别**：告警负责发现，响应负责处理。告警质量决定响应的起点——**告警里没有上下文，响应就要从"先搞清楚怎么了"开始**，而那段时间正是用户受损的时间。
- **与[可观测性](observability.md)的区别**：可观测性提供排查所需的信号。**没有它，复盘只能靠记忆与推测**，结论会退回"我们觉得是因为……"。
- **与[技术债](technical-debt-refactoring.md)的区别**：事故的改进项往往会变成技术债条目。**两者的接口在这里**——复盘产出条目，技术债机制负责不让它们被遗忘。
- **与"追责"的区别**：追责关注"谁做错了"，复盘关注"系统为什么允许这个操作造成这个后果"。同样的操作在更好的系统里可能完全无害。

## 常见误解

1. **先查根因再恢复** → 用户仍在受损，且高压下容易改出新问题。
2. **复盘要有责任人** → 有责复盘得到的是防御性叙述，关键细节会消失。
3. **根因只有一个** → 多因链是常态，只修一点会留下放大因素。
4. **复盘报告写完就算完成** → 改进项没有 owner 与期限等于没做。
5. **事故少就说明系统好** → 也可能是**检测能力差**，事故从未被发现，只以"用户投诉"的形式存在。

## 应用场景

- **该做**：所有生产事故，包括"差点出事"的近似事故（near miss）——后者的改进收益与事故相同，成本低得多
- **判断依据**：问三句——**处置时有没有指定指挥**？**时间线是当场记的还是事后补的**？**上次复盘的改进项现在是什么状态**？
- **配套**：可观测性要能提供时间线素材（事件流、变更记录、指标快照）；改进项纳入技术债管理；**变更记录与事故时间线必须能对齐**（否则无法判断某次事故是否由某次发布引起）
