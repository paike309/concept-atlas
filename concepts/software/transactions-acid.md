## 一句话定义

**中文**：把一组读写操作打包成一个"要么全做、要么全不做"的单元，并保证原子性、一致性、隔离性、持久性四个性质。

**English**: Grouping a set of reads and writes into a single all-or-nothing unit that provides atomicity, consistency, isolation, and durability.

## 我的理解

**ACID 里被误解最多的是 C，而它恰好是唯一一个不由数据库提供的性质。**

- 原子性、隔离性、持久性是数据库**机制**给的：前者靠日志回滚，中者靠锁或版本，后者靠落盘。
- 一致性（Consistency）是**应用**的责任。"转账前后两边余额之和不变"这条规则，数据库不知道，它只知道类型和唯一约束。数据库能做的只是——如果前三个性质不成立，你的不变式更没有机会成立。

由此推出一条更实用的认识：**事务的真实用途是把"可能失败的多步操作"变成一个可以整体重试的单位。** 这一点直接决定了它与[幂等性](idempotency.md)的关系（见「边界」）。

但事务不是免费的。它持有锁与数据版本，**长事务是线上问题的常见根因**，而不是"更安全的选择"。

## 核心机制

**四个性质各自怎么实现**：

| 性质 | 实现机制 | 谁负责 |
|---|---|---|
| 原子性 Atomicity | 预写日志 WAL：先写日志再改数据，崩溃后按日志回滚或重放 | 数据库 |
| 一致性 Consistency | 约束（唯一、外键、检查）能兜住结构层；业务不变式由应用保证 | **应用** |
| 隔离性 Isolation | 多版本并发控制 MVCC 或两阶段锁 | 数据库 |
| 持久性 Durability | 提交返回前日志落盘（fsync），而不是等数据页写回 | 数据库 |

**事务边界**：`BEGIN` → 若干读写 → `COMMIT` 或 `ROLLBACK`。边界该短——它决定了锁的持有时间与版本的生命周期。

**长事务的具体代价**（都能观测到，不是抽象担忧）：

- MVCC 下旧版本无法回收，表与索引膨胀，查询逐渐变慢
- 与其他事务的锁等待概率上升，超时链条变长
- 复制场景下落后的备库要等更长的事务

**隔离性的强弱不由"用了事务"决定**，而由隔离级别决定——这是下一张卡的主题。

## 边界：它不是什么

- **与[隔离级别](transaction-isolation.md)的区别**：事务是**语义单位**（这组操作为什么必须一起生效），隔离级别是**并发规则**（并发事务之间能看到什么）。有了事务不等于有正确的隔离级别。
- **与[幂等性](idempotency.md)的区别**：事务管"一次操作内部要么全成"；幂等性管"同一操作执行多次的净效果"。**关键推论：事务不能让重试变安全。** 提交成功但响应超时，客户端重试会实实在在地再执行一次——事务早已提交，没有回滚的机会。重试需要的幂等键，事务给不了。
- **与分布式一致性模型的区别**：ACID 的 C 是**应用不变式**；分布式系统里的 C（线性一致、最终一致）说的是**多副本之间的可见性**。**同一个字在两个语境里不是一件事**——这是本领域最容易混的术语陷阱。

## 常见误解

1. **ACID 的 C 就是 CAP 的 C** → 不是。前者是应用不变式，后者是副本一致性模型。
2. **用了事务就没有并发问题** → 隔离级别决定可见性与异常，默认级别通常低于可串行化。
3. **事务范围越大越安全** → 长事务带锁等待、版本堆积、复制滞后，是故障来源。
4. **事务能防止重复提交** → 不能。客户端超时重试是在事务提交**之后**发生的。
5. **跨服务的分布式事务是首选方案** → 大多数业务用"幂等 + 补偿"更合适；跨服务两阶段提交把可用性绑在了所有参与方上。

## 应用场景

- **该用**：多步写入必须同步生效（扣款与记账）、读-判断-写序列（库存扣减）、任何"中间失败会留下矛盾数据"的操作
- **不该用**：跨服务的强一致写入（优先用幂等与补偿）、长流程（用状态机 + 最终一致）、单条只读查询
- **判断依据**：问"**这组操作中间失败时，系统能自己察觉并修复吗？**"不能 → 需要事务；能 → 用更轻的机制
- **配套**：一旦有重试，就必须有[幂等性](idempotency.md)；一旦有并发，就必须想清[隔离级别](transaction-isolation.md)
