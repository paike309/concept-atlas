## 一句话定义

**中文**：在隔离外部依赖的条件下验证单个逻辑单元的测试，以及为支撑它而需要的设计性质（可测性）。

**English**: Testing a single logical unit with external dependencies isolated — plus the design properties (testability) that make it possible.

## 我的理解

单元测试的困难从来不在"写断言"，而在**可测性**。

一个类如果自己 `new` 依赖、自己读时钟、自己发网络请求，就没法在隔离条件下测。**这不是测试技巧问题，是设计问题。**

所以：

> **"难测"是设计的信号，不是测试的障碍。**

遇到难测的代码，正确的反应是改设计——把依赖注入、把副作用推到边界、把纯逻辑与 IO 分开——而不是用越来越复杂的桩去绕过它。

另一个关键点：单元测试隔离的是**外部依赖**（文件、网络、时钟、随机、数据库），**不是"所有其他类"**。把所有协作者都替换成桩，会得到"测桩本身"的测试——断言全绿，但什么都没验证。

## 核心机制

**单元边界的选择**：通常是一个类或一组紧密协作的类。**边界由行为决定，不由文件决定。**

**替身的选择**（这是最容易做错的地方）：

| 类型 | 是什么 | 适用 |
|---|---|---|
| **Fake** | 可工作的简化实现（如内存存储） | **优先** |
| Stub | 返回预设值 | 只需要固定返回值时 |
| Mock | 可断言被如何调用 | 必须验证交互时 |
| Spy | 记录调用 | 排查用 |

**优先用 fake**：它不绑定调用细节，重构时不易碎；它验证的是行为，而不是"你有没有按我设想的方式调用"。

**断言什么**：断言**可观察的行为与结果**，不是内部调用顺序。断言调用细节的测试会在重构时大面积失败——这是测试变成负债的主要途径。

**不碰的东西**：时间、随机、网络、文件系统、并发。这些必须被推到边界并通过参数注入。

**可测性的三个来源**：

1. 依赖通过参数进入（而不是内部构造）
2. 副作用集中在少数边界
3. 纯逻辑与 IO 分离

## 边界：它不是什么

- **与集成测试的区别**：是否使用真实外部组件。单元测试用替身，集成测试用真货。
- **与"测试私有方法"的区别**：测行为，不测实现。私有方法的行为应该通过公开接口间接覆盖——直接测私有方法会把测试焊死在实现上。
- **与[契约测试](contract-testing.md)的区别**：契约测试关注**两个组件之间的约定**，不关注单个组件的逻辑。

## 常见误解

1. **单元测试就是每个函数写一个测试** → 边界由行为决定，不按函数机械划分。
2. **覆盖率是目标** → 覆盖率是副产物。目标是验证行为；高覆盖率可以全是弱断言。
3. **mock 越多越隔离** → 过度 mock 会产出脆弱且什么也不验证的测试。优先用 fake。
4. **难测就多写桩** → 难测是设计问题，加桩只是把问题从设计层转移到测试层。

## 应用场景

- **该做**：核心业务规则、边界条件、错误路径
- **不必做**：纯数据类、框架生成的代码、一次性脚本
- **判断依据**：**如果一个模块改实现就要改大量测试，说明测试绑定了实现细节**——这是最实用的诊断信号
