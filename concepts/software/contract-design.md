## 一句话定义

**中文**：接口设计时明确输入输出的约定——必填与可选、取值范围、错误语义、幂等性、兼容性承诺。

**English**: Specifying the interface agreement — required versus optional, value ranges, error semantics, idempotency, and compatibility promises.

## 我的理解

契约设计的核心是**把"调用方可以依赖什么"写清楚**。它决定了三件事：

1. 调用方能做哪些假设（决定他们怎么写代码）
2. 你能在不破坏别人的前提下改什么
3. [版本号](semantic-versioning.md)该升哪一位

三个最常被漏掉的约定：

| 漏掉的约定 | 后果 |
|---|---|
| **错误语义**（哪些可重试） | 调用方对不该重试的错误做重试 |
| **幂等性** | 重试变成碰运气（见[幂等性](idempotency.md)） |
| **顺序与一致性**（强一致还是最终一致） | 调用方假设强一致，然后偶尔出错 |

一条原则：**契约要向前兼容地演进。**

加可选字段是兼容的；加必填字段、改字段含义、改默认行为都是破坏性的。

**最难处理的是语义变更**：结构没变、含义变了。任何静态检查都发现不了，**只有了解语义的人能识别**。这类破坏性变更最容易造成生产事故。

## 核心机制

**契约的三个组成部分**：

| 部分 | 内容 |
|---|---|
| 结构 | 字段与类型 |
| 语义 | 字段含义、单位、取值范围 |
| 行为 | 错误、幂等性、一致性、超时预期 |

**兼容性规则**：

| 变更 | 是否兼容 |
|---|---|
| 加可选字段 | 兼容 |
| 放宽取值范围 | 兼容 |
| 加必填字段 | **破坏** |
| 删除字段 | **破坏** |
| 改字段类型 | **破坏** |
| **改字段含义** | **破坏（最难发现）** |
| 收窄取值范围 | **破坏** |
| 改默认行为 | **破坏（隐性）** |

**表达方式**：schema（结构）+ 可执行[契约测试](contract-testing.md)（语义）。**schema 表达不了语义。**

**版本策略**：URL 版本、请求头版本、或纯演进式（只做兼容变更）。演进式成本最低，但要求最严。

## 边界：它不是什么

- **与 API 文档的区别**：契约包含**可检查的承诺**，文档只是描述。没有可执行检查的文档会漂移。
- **与[契约测试](contract-testing.md)的区别**：契约测试**验证**契约，契约设计**定义**契约。先有定义才能验证。
- **与版本号的区别**：版本号表达**兼容性结论**，契约定义**兼容性内容**。

## 常见误解

1. **有文档就够了** → 文档会漂移，需要可执行检查。
2. **改含义不算破坏性变更** → 结构没变所以检查不到，**是最危险的一类**。
3. **加字段总是安全的** → 加**必填**字段不安全。
4. **演进式版本不可能** → 可以，只是对纪律要求严格。

## 应用场景

- **该做**：所有对外或跨团队的接口
- **判断依据**：写下"**调用方可以依赖这个接口的哪些性质**"。写不出来，说明契约还没定义，调用方只能靠猜——**猜错就是生产事故**
- **配套**：把关键承诺写进可执行的契约测试，让它变成 CI 检查而不是文档条款

## 自测

1. 结构没变但含义变了，为什么是最危险的变更？怎么防？
2. 默认值为什么属于契约的一部分？
3. schema 覆盖不了契约的哪一部分？那部分该怎么表达？
