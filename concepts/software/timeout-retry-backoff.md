## 一句话定义

**中文**：处理外部调用失败的三件套——超时（放弃等待）、重试（重新尝试）、退避（拉长重试间隔）。

**English**: The trio for handling external call failures — timeout (stop waiting), retry (try again), backoff (widen the interval).

## 我的理解

这三者必须**同时存在**。任意两个都会出问题：

| 缺什么 | 后果 |
|---|---|
| 缺重试 | 一次网络抖动就失败 |
| 缺超时 | 挂住的调用占满资源；重试变成故障放大器 |
| 缺退避 | 失败的服务被瞬间淹没，**把可恢复故障变成不可恢复** |

核心认识：**重试是一种故障放大器。**

当依赖整体不可用时，重试会把请求量乘以重试次数，反而延长故障时间。所以它必须配合退避、抖动和熔断。

第二个关键认识：**重试的前提是幂等。**

不幂等的操作重试会造成重复副作用——重复下单、重复扣款。做不到幂等就必须放弃自动重试，或者引入去重键。**这一条比调参重要得多。**

## 核心机制

**超时**：

- 取值依据是依赖的 **P99 延迟 × 安全系数**，不是拍脑袋。太短会误杀正常请求，太长会把下游故障传导成上游资源耗尽
- **分层次设置**：连接超时、读取超时、总超时，三者分别设。**只有总超时会掩盖问题**——你不知道是连不上还是处理太慢

**重试次数与预算**：

- 绝对次数（如 3 次），或
- **重试预算**：限制重试流量占总流量的比例上限。**预算制更安全**，因为它能自动适应故障规模

**指数退避**：间隔按倍数增长（1s → 2s → 4s），避免持续冲击。

**抖动（jitter）**：在退避间隔上加随机量。

> **没有抖动时，所有客户端会同步重试，形成周期性的冲击波。** 这是最容易漏掉的一点，也是"加了退避还是被打垮"的常见原因。

**熔断**：连续失败达阈值后直接拒绝，快速失败而不消耗资源；半开状态用于探测恢复。它与重试的分工是：**重试是继续尝试，熔断是暂时放弃。**

**只重试可重试的错误**：

| 可重试 | 不可重试 |
|---|---|
| 连接错误、超时 | 参数错误（4xx） |
| 服务端错误（5xx） | 鉴权失败 |
| 限流响应（需配合退避） | 业务规则拒绝 |

**幂等保障**：去重键（idempotency key）、唯一约束、操作状态标记。三者至少用其一。

## 边界：它不是什么

- **与熔断的区别**：重试继续尝试，熔断暂时放弃。两者配合——重试到阈值后熔断。
- **与限流的区别**：限流控制**入口速率**，重试是**内部放大**。只做限流不做重试预算是半套方案。
- **与队列/异步的区别**：异步把同步等待变成排队，改变了失败模型（失败变成积压），不是简单的优化。

## 常见误解

1. **多试几次总没错** → 不幂等时会造成重复副作用。
2. **重试不需要退避** → 会造成重试风暴。
3. **退避就够了，不用抖动** → 同步重试形成冲击波。
4. **超时设长一点更安全** → 长超时会把下游故障传导为上游资源耗尽。

## 应用场景

- **该用**：任何跨进程调用
- **该先确认**：被调操作是否幂等、失败是否可重试
- **判断依据**：写下"**这个调用失败时会重试几次、间隔多少、最坏情况下会不会重复执行副作用**"。写不出具体数字就不要上线
- **配套**：没有[可观测性](observability.md)，你无法判断重试是在缓解还是在放大问题
