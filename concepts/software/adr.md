## 一句话定义

**中文**：把一次重要技术决策的背景、选项、结论与后果记录成简洁文档，随代码一起版本化。

**English**: Recording the context, options, decision, and consequences of a significant technical choice in a short document versioned alongside the code.

## 我的理解

它的价值在于**记录"为什么"，而不是"是什么"**。

代码和文档能告诉你系统现在的样子，但回答不了"**当初为什么不选另一个方案**"。

这个信息会以两种方式丢失：写代码的人离开，或者写代码的人自己忘了——**几个月后你也会忘记当时的约束**。

格式上只需要几段：背景（当时的约束）、选项、决定、后果。**关键是"后果"必须写代价**——只写优点的决策记录等于宣传材料，没有参考价值。

ADR 是**不可变**的：决策变了就写一个新的，并标明取代哪个旧的。这保留了演进的轨迹，而不是抹掉历史。

一句务实的判断：**ADR 的性价比极高。** 几行字，替代的是未来一次完整的重新论证。这也是它在"最容易被跳过"和"收益最高"之间形成反差的原因。

## 核心机制

**典型结构**：

| 字段 | 内容 |
|---|---|
| 标题 | 编号 + 决策名 |
| 状态 | 提议 / 接受 / 被取代 / 废弃 |
| 背景 | 当时的约束与问题 |
| 决策 | 选了什么 |
| **后果** | 得到什么、**付出什么代价** |
| 备选方案 | 考虑过什么、为什么不选 |

**不可变性**：不修改已接受的 ADR，用新的 ADR 取代它，形成链。

**存放位置**：与代码同一个仓库（如 `docs/decisions/`），因此可以被 diff、被引用、被一起审查。

**粒度**：只记录"**难以逆转**"或"**会造成分歧**"的决策，不要每个小决定都记。

**与[变更日志](changelog.md)的分工**：ADR 回答"为什么这么选"，changelog 回答"变了什么"。

## 边界：它不是什么

- **与设计文档的区别**：设计文档描述**系统方案**（可能很长）；ADR 记录**决策与理由**（一页内）。
- **与变更日志的区别**：见上。
- **与代码注释的区别**：注释解释局部实现；ADR 解释全局取舍。两者层级不同。

## 常见误解

1. **只有重大决策才需要** → 标准是"难逆转或会有分歧"，不是"听起来重大"。
2. **可以事后再补** → 会丢失当时的约束，补出来的是**合理化后的理由**，不是真实原因。
3. **ADR 要写得详细** → 一页内即可。重点是理由与代价。
4. **决策变了要修改旧 ADR** → 应写新的并标明取代旧的那一条。

## 应用场景

- **该做**：选型决策（框架、协议、存储）、结构性取舍（分层方式、边界划分）、有争议的约定、**被否决的提案**（记录下来避免重复讨论）
- **判断依据**：问"**如果半年后有人问为什么这么做，我不在场能答上来吗？**"
- **配套**：在[代码审查](code-review.md)中要求结构性变更附带 ADR

## 自测

1. ADR 记录的是"是什么"还是"为什么"？用一个具体例子说明差别。
2. 为什么 ADR 必须不可变？
3. "后果"一节为什么必须包含代价？只写优点会有什么问题？
