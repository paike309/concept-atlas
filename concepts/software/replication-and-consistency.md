## 一句话定义

**中文**：把同一份数据保存在多个节点上（复制），并规定任意副本上读到的内容允许有多旧（一致性模型）。

**English**: Keeping copies of the same data on multiple nodes, and specifying how stale a read from any replica is allowed to be.

## 我的理解

**复制解决的问题和它引入的问题一样清楚。**

它要解决的：一个节点挂了还有别的（可用性）、多个节点分担读流量（吞吐）、就近读取（延迟）。

它引入的：**同一份数据有了多个版本，"读到的到底算不算最新"变成了一个必须回答的问题**——这就是一致性模型。

由此得到两条认识：

1. **一致性模型不是"好/坏"的口号排序，而是对读写可见性的契约。** 选哪个，取决于"读到 5 秒前的数据，业务会怎样"。这把问题从"哪个更强"换成了"哪种陈旧度可接受"——**和[范式化](normalization.md)那张卡里的判断方式是同一个形状**。
2. **它和隔离级别是两层，不是一回事。** 隔离级别管的是一个数据库**内部**并发事务之间的可见性；一致性模型管的是**跨副本**的读写顺序。跨节点部署时，两层同时生效，且**后者无法被前者覆盖**。

最关键的一条边界见「边界」一节：**复制不是备份。**

## 核心机制

**复制拓扑**：

| 拓扑 | 写入路径 | 特点 |
|---|---|---|
| 单主（主从） | 只有一个节点接受写 | 最简单、最常用；主库是写入上限与单点 |
| 多主 | 多个节点都能写 | 写入可用性高，代价是写冲突需要解决策略 |
| 无主（quorum） | 客户端写多个节点 | 用读写副本数配比换取一致性强度 |

**同步复制 vs 异步复制——这是最常被忽略的一组取舍**：

| | 主库何时返回成功 | 代价 |
|---|---|---|
| 同步复制 | 至少一个副本确认之后 | 副本变慢会直接拖慢写入；副本不可用时可能阻塞 |
| 异步复制 | 主库本地写完就返回 | 主库故障时**可能丢失最后一段已确认的写入** |

**读写副本数与一致性**：在无主复制里，写入确认数 W、读取询问数 R、副本总数 N 满足 `W + R > N` 时，读集合与写集合必然相交，读才能保证看到最近一次写入。**这个不等式的直觉是"读写必须有重叠"，而不是背公式。**

**常见的一致性模型**（从强到弱，不是精确的全序，而是常用谱系）：

| 模型 | 保证 |
|---|---|
| 线性一致 Linearizable | 整个系统看起来只有一个副本，任何读都能看到最近一次成功写入 |
| 顺序一致 Sequential | 所有节点看到相同的操作顺序，但该顺序不一定等于真实时间顺序 |
| 因果一致 Causal | 有因果关系的操作顺序被保留；无因果关系的可以不同 |
| 最终一致 Eventual | 停止写入后，副本最终会收敛到同一状态 |

**复制滞后（replication lag）导致的两类日常现象**：

- **读己之写失败**：写入后立刻从只读副本读，读不到自己刚写的内容（请求被路由到了尚未同步的副本）
- **单调读违例**：同一个会话先读到新值，刷新后又读到旧值（两次读落到进度不同的副本上）

## 边界：它不是什么

- **与[隔离级别](transaction-isolation.md)的区别**：隔离级别是**单库内、事务之间**的可见性规则；一致性模型是**跨副本、单对象**的读写顺序保证。两者层级不同，可以叠加，也可以互相独立——**在只读副本上就算用了可串行化，读到的仍然是副本的旧快照**。
- **与备份的区别**：这是最容易致命的一条。备份是**离线的、某个时间点的**数据副本，用于灾难恢复；复制是**在线的、持续的**同步。**误删一张表，删除会照样同步到所有副本**——复制不提供任何"回到删除前"的能力。
- **与[分片](sharding-and-partitioning.md)的区别**：复制是同一份数据的多份拷贝（提高可用性与读吞吐），分片是不同数据分散到不同节点（提高容量与写吞吐）。两者正交，生产系统通常同时用。
- **与"最终一致 = 没设计好"的区别**：最终一致是有明确语义的工程选择，代价被**显式转移给应用**（幂等写入、版本号比较、读己之写兜底）。真正的缺陷不是最终一致，而是**选了它却没处理陈旧读**。

## 常见误解

1. **配置了主从就是高可用** → 异步复制下主库故障可能丢失已确认写入；没有自动故障转移机制时，仍然需要人工介入。
2. **有副本就可以随意做读负载均衡** → 异步复制下读副本会读到旧数据，"读己之写"会失败。
3. **最终一致"过一会儿"就一致了** → 它没有时间上界。复制延迟在备份、大事务、网络抖动时可能持续放大。
4. **复制等于备份** → 见「边界」。这是两个用途完全不同的机制。
5. **一致性越强越好** → 线性一致要求多数派确认，代价是延迟与分区时的可用性。**强度是要买的。**

## 应用场景

- **该用同步复制**：不允许丢失已确认写入的场景（账务、订单），且能接受写入延迟上升
- **该用异步 + 读主库**：需要"读己之写"的交互路径——写入后的那次跳转直接从主库读
- **判断依据**：问"**如果这次读到的是 5 秒前的数据，业务上会发生什么**"。答案是"没关系"→ 可以读副本；是"用户会以为提交失败了"→ 该路径必须读主库或做版本校验
- **配套**：跨副本重试必须[幂等](idempotency.md)；复制延迟必须在[可观测性](observability.md)里有指标，否则"偶发的数据不对"无从排查
