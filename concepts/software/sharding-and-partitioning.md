## 一句话定义

**中文**：把大数据集按规则切分到多个节点（分片），或在单库内把一张大表切成多个物理块（表分区）。

**English**: Splitting a large dataset across multiple nodes (sharding), or dividing one large table into several physical pieces within a single database (partitioning).

## 我的理解

**中文里这两个词经常被混用，但它们解决的问题不同，而且不能互相替代。**

| | 表分区 Partitioning | 分片 Sharding |
|---|---|---|
| 范围 | 单库内 | 跨节点 |
| 解决 | 查询裁剪、维护与归档（按分区批量删除） | 单机容量与写入上限 |
| 代价 | 分区键之外的查询要扫多个分区 | 跨分片查询/事务变成分布式问题 |

由此推出两条最重要的判断：

1. **分片是不可逆的架构决策，不是性能优化。** 分片键一旦选定、数据写进去，改分片键意味着跨节点重分布——成本接近重做。所以它必须放在决策顺序的最后：**单库优化（索引、查询、归档）→ 读写分离与复制 → 表分区 → 最后才是分片。**
2. **分片键的选择决定了后续几乎所有问题**：写入是否均匀、高频查询能否只落一个分片、业务不变式能否在一个分片内完成。**先想清楚"我最高频的那条写入和那条查询分别是什么"，再选键**——顺序反了就只能靠跨分片聚合来补。

## 核心机制

**三种分片方式**：

| 方式 | 优点 | 缺点 |
|---|---|---|
| 范围分片 | 范围查询高效、便于按时间归档 | 容易热点——按时间分片时最新分区永远最热 |
| 哈希分片 | 分布均匀 | 丧失范围查询能力（相邻键散落各节点） |
| 目录 / 查表分片 | 灵活、可人工干预热点 | 路由表本身成为必须高可用的组件 |

**路由方式**：应用层路由（自己实现分片逻辑）或在中间件/代理层路由。前者灵活，后者让应用代码保持简单——**但无论哪种，跨分片的能力都要单独设计**。

**再平衡（rebalancing）**：节点增减时需要迁移数据。**用"固定分片数 + 映射表"或一致性哈希，不要用 `hash(key) % 节点数`**——后者在节点数变化时几乎全部数据都要重新分布。

**跨分片操作的代价**：

- 跨分片查询要**扇出 + 聚合**（scatter-gather），尾延迟由最慢的分片决定
- 跨分片事务要么用两阶段提交（把可用性绑在所有参与方上），要么**在设计上避免**——把需要原子性的数据放在同一个分片内，这正是分片键选择的核心约束

**热点问题**：即使哈希足够均匀，**单个超热键（大 V、超级租户）仍然会全部落到一个分片**。缓解方式是应用层拆分（热键加后缀/加盐、按时间再切一层），而不是换哈希函数。

**表分区的实际收益**：分区裁剪（只扫相关分区）、按分区批量删除或归档历史数据、分区级索引维护。**它的前提是查询里带上了分区键**——不带就退化为扫描所有分区。

## 边界：它不是什么

- **与[复制](replication-and-consistency.md)的区别**：复制是**同一份数据的多份拷贝**（提高可用性与读吞吐），分片是**不同数据分散到不同节点**（提高容量与写吞吐）。两者正交互补，生产系统通常同时使用。
- **与表分区的区别**：见「我的理解」。一个是单库内的物理组织，一个是跨节点的数据分布——**表分区不需要改应用架构，分片需要**。
- **与按业务拆库的区别**：按业务边界把不同表拆到不同库是**垂直拆分**，同一张表按行切到多个库是**水平拆分**。维度不同，垂直拆分不解决"单表太大"，水平拆分不解决"业务耦合"。
- **与[索引](index-and-query-plan.md)的区别**：索引在一张表内加速定位；**索引解决不了"单机装不下、写不进"**。反过来，分片也修不了缺少索引带来的全表扫描。

## 常见误解

1. **分片能提升性能** → 它提升的是容量与写入上限；**跨分片查询往往比单库更慢**，因为要扇出并等待最慢的分片。
2. **分片键以后可以改** → 代价是跨节点重分布，接近重做数据层。
3. **哈希分片就没有热点** → 超热单一键仍会打到一个分片，需要应用层再拆。
4. **表分区就是分片** → 单库内与跨节点是两件事，前者不改应用架构。
5. **分片后还能像以前一样查询** → 跨分片 JOIN、聚合、排序都变成分布式问题，要么避免、要么接受复杂度。

## 应用场景

- **该分片**：单表数据量或写入量已超出单机可靠范围，且已穷尽单库手段（索引优化、归档、读写分离、表分区）
- **不该分片**：还能靠上述手段撑住时——分片引入的复杂度是**永久成本**，而容量问题往往是阶段性的
- **判断依据**：先算三个数——**单机当前容量上限、当前实际用量、增长速度**；再问"除了分片，还剩哪些手段没用"
- **选择分片键的依据**（三条同时满足）：写入分布均匀 · 最高频查询只落一个分片 · 值本身稳定不变
- **配套**：[可观测性](observability.md)要按分片维度观测（否则热度不均发现不了），[背压](backpressure.md)要能对单个分片生效
