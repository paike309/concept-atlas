## 一句话定义

**中文**：高层模块不应依赖低层模块，两者都应依赖抽象；抽象不应依赖细节，细节应依赖抽象。

**English**: High-level modules should not depend on low-level modules; both should depend on abstractions, which in turn should not depend on details.

## 我的理解

这条原则常被简化成"面向接口编程"，但它解决的问题更具体：**依赖方向决定了改动的传导方向。**

常规依赖是"业务流程调用数据库"，于是业务层依赖数据库的技术细节。换数据库就要改业务层——这显然是错的，因为**业务规则比数据库选型稳定得多**。

倒置的做法是**把接口的定义权交给高层**：业务层定义"我需要一个能存订单的东西"，具体实现去适配这个接口。依赖箭头反转，数据库变成可替换的插件。

**关键判断：接口应该由调用方定义，而不是由实现方定义。**

这一条经常被做反——库作者定义一堆接口，使用者被迫依赖库的内部结构。做反了，依赖方向其实没变，只是多了一层。

## 核心机制

**依赖方向的含义**：A 依赖 B 意味着 A 的编译/部署需要 B。倒置后引入抽象层 I，变成 A→I←B。

**接口归属**：

| | 归属 | 特性 |
|---|---|---|
| 接口 | **高层**（稳定的策略） | 变化慢 |
| 实现 | 低层（易变的细节） | 变化快 |

**稳定性排序依据**：越抽象、越接近业务规则的东西越稳定，应放在内层。

**与依赖注入的关系**：倒置是"往哪依赖"（结构目标），注入是"怎么把实现传进来"（达成手段）。**两者可以独立存在**——用注入但没有倒置（业务层仍 import 具体类）是常见状态。

**代价**：多一层间接、多一个需要维护的接口。

## 边界：它不是什么

- **与[依赖注入](dependency-injection.md)的区别**：见上。用了 DI 容器不等于实现了倒置。
- **与"分层"的区别**：分层是物理切分，倒置是依赖方向的**规定**。两者常配合使用，但不能互相替代。
- **与"为所有东西建接口"的区别**：只为**会被替换或需要隔离**的依赖建接口。对不变的东西建接口是纯成本。

## 常见误解

1. **依赖倒置就是多用接口** → 接口是手段。乱建接口只增加间接层，不改变依赖方向。
2. **接口定义在实现方那一侧** → 做反了。等于把依赖方向原样保留，还多加了一层。
3. **所有依赖都要倒置** → 对标准库、语言本身这类不变量做倒置是浪费。
4. **用了 DI 容器就实现了倒置** → 容器只是装配工具。业务层仍 `import` 具体实现类，方向就没变。

## 应用场景

- **该用**：外部依赖会变（数据库、第三方服务、文件系统、时钟）；需要隔离以便测试
- **不该用**：不变量——标准库、语言特性、稳定的基础设施
- **判断依据**：问"**这个东西换掉的概率有多大**"。概率高才值得引入抽象
- **落地检查**：看内层代码的 import 列表。如果有任何框架或数据库驱动的名字，方向就破了
