## 一句话定义

**中文**：一个操作重复执行多次与执行一次的效果相同。

**English**: An operation whose repeated execution has the same effect as executing it once.

## 我的理解

它的价值在于**让重试成为可能**。

没有幂等性，重试就是"可能重复副作用"的赌博（见[超时、重试与退避](timeout-retry-backoff.md)）。所以幂等性不是可选优化，**它是重试的前提条件**。

关键在区分两类操作：

| 类型 | 例子 |
|---|---|
| 天然幂等 | 把某值设为 X、删除某资源、查询 |
| **需要额外设计** | 增加计数、追加记录、扣款、发送消息 |

第二类需要引入去重机制，常见三种：

1. **幂等键**：调用方生成唯一键，服务端记录已处理的键
2. **唯一约束**：数据库层面防止重复插入
3. **状态机**：只允许合法状态转移，重复请求因状态不匹配被拒绝

一条必须说清的事实：**"恰好一次"是做不到的。**

分布式环境下只能在"至少一次 + 幂等"和"至多一次 + 可能丢失"之间选。所以现实做法是**至少一次投递 + 幂等处理**。

## 核心机制

- **幂等键的要点**：由**调用方**生成（不是服务端）；键在重试时必须保持不变；服务端保存已处理的键**连同结果**，重复请求直接返回原结果
- **存储窗口**：幂等键不能永久保存，需要过期策略——**窗口必须长于最大重试窗口**
- **并发下的原子性**：两个相同键的请求同时到达时，"检查—然后—写入"必须原子（唯一索引或事务），否则依然会重复
- **副作用拆分**：把不可幂等的副作用（发邮件、调用外部接口）放到确认成功之后，或者同样加去重
- **与状态机的配合**：用状态转移代替布尔标记，重复请求自然被拒绝
- **顺序问题**：幂等只保证"不重复"，**不保证顺序**。需要顺序时要另加序列号

## 边界：它不是什么

- **与事务的区别**：事务保证一组操作的**原子性**；幂等保证**重复执行的安全**。二者解决不同问题，常需配合。
- **与重试的区别**：重试是**发起方**行为，幂等是**被调方**的性质。前者可以随便加，后者必须被设计出来。
- **与"去重"的区别**：去重是**手段**，幂等是**目标**。且去重本身需要窗口与原子性保证。

## 常见误解

1. **网络层会自动去重** → 不会。网络只保证传输，不保证副作用只发生一次。
2. **重试次数少就不用管** → 概率低，但影响可能不可逆（重复扣款）。
3. **有唯一约束就完全幂等** → 只覆盖插入类操作，覆盖不了"更新计数"这类。
4. **幂等就是"最终结果一样"** → 还要看**副作用层面**：是否重复发了消息、重复扣了款。

## 应用场景

- **该做**：任何会被重试的写操作、任何消息消费、任何支付或计费
- **判断依据**：问"**这个操作执行两次会怎样？**" 答案不是"没影响"，就必须加去重机制
- **配套**：在[接口契约](contract-design.md)里明确写出哪些接口是幂等的——这是调用方决定能否重试的唯一依据
