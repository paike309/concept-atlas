## 一句话定义

**中文**：用版本历史记录变更、用分支隔离并行工作、用合并策略把变更汇入主线的做法。

**English**: Recording changes as history, isolating parallel work with branches, and merging changes back into a mainline.

## 我的理解

版本控制的核心价值不是"备份"，**是"可追溯的变更单元"**。

备份回答"能不能回到昨天"；版本控制回答"**这行为什么变成现在这样**"。前者是数据安全，后者是认知工具。混淆这两者，就会把版本控制当运维设施，而不是开发工具。

分支策略要解决的权衡只有一个：**隔离度 vs 集成频率**。

分支活得越久，隔离越好，但合并冲突越大、集成风险越集中——这是"合并地狱"的根源。所以主流实践的方向都是**缩短分支寿命**。

一个容易忽略的点：**提交历史的可读性是一种资产**。一年后 debug 时，一条说明"为什么"的提交信息，比一百条"fix bug"有用。

## 核心机制

**三个基本操作**：提交（原子变更 + 说明）、分支（并行工作线）、合并（把一条线汇入另一条）。

**合并与变基的区别**：

| | 合并 merge | 变基 rebase |
|---|---|---|
| 历史形状 | 保留分叉与合并点，是真实的图 | 线性，看起来像顺序开发 |
| 提交哈希 | 不改写 | **改写**（重放到新基点） |
| 使用前提 | 总是安全 | **未推送的提交**才可变基 |

已推送的提交变基会给协作者制造混乱——这是新手最常踩的坑。

**冲突的本质**：同一段代码在被分叉的两条线上都被修改。**冲突规模与分支寿命正相关。**

**主流策略的取舍**：

| 策略 | 特点 | 代价 |
|---|---|---|
| 主干开发 trunk-based | 小步频繁合入主干，未完成功能用特性开关隐藏 | 要求自动化测试足够强 |
| 长分支（Git Flow 类） | 适合有明确发布周期、多版本并行的产品 | 长期分支 + 复杂合并 |

经验规则：**超过几天的分支就该重新审视**。

**与发布的关系**：分支策略决定了"一个版本包含哪些变更"能不能被回答。若回答不了，**回滚也会变得困难**。

**提交粒度**：一个提交应该是一个可解释的变更单元（能编译、能通过测试、说明"为什么"）。**不要把重构与功能改动混在一个提交里**——想回滚功能时会连带回滚重构。

## 边界：它不是什么

- **与代码审查的区别**：分支与合并是机制，审查是在这个机制上加的流程节点。没有分支也能审查（主干开发下用变更请求）。
- **与发布策略的区别**：分支管"代码怎么汇合"，发布管"什么时候给用户"。两者常被混谈，但可独立设计。
- **与持续集成的区别**：CI 是自动化验证，分支策略决定它的**触发频率与有效性**。长期分支会让 CI 的价值大幅下降——集成问题被推迟到合并那一刻集中爆发。

## 常见误解

1. **分支越多越安全** → 分支是隔离手段，不是安全手段。长期分支累积的是**风险**，不是安全。
2. **变基比合并干净所以更好** → 前提是这些提交还没被共享。已推送的提交变基会破坏协作者的历史。
3. **提交信息写 "fix" 就行** → 提交信息是给未来的自己看的。**写"为什么"，不写"做了什么"**——做了什么看 diff 就知道。
4. **必须选一种流派并严格遵守** → 策略应匹配团队规模与发布节奏。照搬流程往往比没有流程更糟。

## 应用场景

- **该做**：任何多人协作的代码库；任何需要回答"这个版本包含什么"的场景
- **判断依据**：能不能回答两个问题——"这个版本包含哪些变更"、"每条变更为什么在这"。答不出就需要改策略
- **配套**：与语义化版本、变更日志配合，才构成完整的变更管理链
