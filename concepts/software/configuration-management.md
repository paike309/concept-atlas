## 一句话定义

**中文**：把随环境变化的值与不随环境变化的逻辑分开管理，并且让前者也可版本化、可审计、可回滚。

**English**: Managing environment-varying values separately from environment-invariant logic, with the values themselves versioned, auditable, and revertible.

## 我的理解

**判断"某个东西是不是配置"，标准只有一条：它在不同环境之间会不一样吗？**

- 会不一样 → 配置（数据库地址、外部服务端点、配额、开关）
- 一样 → 代码（业务逻辑、算法）

这条线划清之后，"同一个制品在所有环境都能跑"才有可能——因为**制品里不含环境特定的东西**。这也是[可复现构建](reproducible-build.md)能成立的前提之一：构建一次、处处运行，靠的正是配置与代码分离。

三条实践结论：

1. **配置要像代码一样对待**：版本化、可评审、可回滚、有变更记录。**配置错误的破坏力与代码错误同级**——它是不停机就能打挂全站的一类变更。
2. **密钥不是配置。** 它有独立的生命周期（轮换、撤销、最小权限、不进日志），不能和普通配置放同一条通道（见[加密与密钥管理](encryption-and-key-management.md)）。
3. **配置漂移是默认结果，不是意外。** 只要允许手工改动环境里的配置，它就会与版本库里的定义不一致，而**这种不一致通常只在故障排查时被发现**——那时你看到的系统状态与代码里的定义已经不同了。

## 核心机制

**分层与作用域**（避免把"配置"当成一个平铺的键值堆）：

| 层级 | 例子 | 变更频率 |
|---|---|---|
| 环境级 | 外部服务端点、资源配额 | 低 |
| 服务级 | 超时值、重试次数、连接池上限 | 中 |
| 功能级 | 开关、灰度比例 | 高 |

分层的意义在于**变更影响面**：环境级改错影响所有服务，功能级改错只影响一个功能。审批与回滚策略应该与其影响面匹配。

**配置的错误形态**：

| 形态 | 表现 |
|---|---|
| 类型错 | 字符串 `"false"` 被当成真值（**高频且隐蔽**） |
| 缺失 | 用默认值静默启动，行为与预期不符 |
| 环境不一致 | 预发与生产行为不同，问题无法在预发复现 |
| 漂移 | 线上被手工改过，版本库里查不到 |

**配置校验应当在启动时失败，而不是运行时**：启动即校验（必填项、取值范围、互相依赖的项），让错误在部署阶段暴露，而不是在第一个用户请求时暴露。**"用默认值兜底启动成功"是最危险的配置策略**——它把配置错误变成了运行时的行为异常。

**配置变更要走发布流程**：谁改、改了哪个键、影响哪些实例、如何回滚。配置热更新（不重启生效）很方便，但它把"变更"从部署里剥离了出来，**如果没有配套的变更记录，出事后将无法把故障与变更关联起来**。

## 边界：它不是什么

- **与[代码](reproducible-build.md)的区别**：代码定义**行为**，配置选择**环境相关的具体值**。混淆两者的后果是同一个制品在不同环境表现不同，且无法复现。
- **与[密钥管理](encryption-and-key-management.md)的区别**：密钥的威胁模型不同（泄露即失守），生命周期不同（必须轮换），存放要求不同（KMS/HSM），**只是"都长得像键值对"**。
- **与[基础设施即代码](infrastructure-as-code.md)的区别**：IaC 管的是**资源本身**（机器、网络、数据库实例），配置管理管的是**应用与环境的参数**。两者都会遇到漂移问题，处理方法同源。
- **与功能开关的区别**：开关是配置的一种，但它的生命周期管理（过期清理）是独立问题，不能被笼统的"配置管理"覆盖。

## 常见误解

1. **配置用默认值兜底更健壮** → 它把配置错误从部署期推到运行期，问题更难定位。
2. **配置改动不用评审** → 配置是最容易触发的变更类型，也是影响面最大的之一。
3. **密钥和配置放一起方便** → 权限模型与轮换需求完全不同。
4. **热更新就等于安全变更** → 少了重启这道"自然闸门"，变更与故障的因果关联反而更难建立。
5. **环境之间配置不同是正常的、不用对齐** → 需要区分"**有意不同**"与"**意外漂移**"，后者的数量应持续压到接近零。

## 应用场景

- **该做**：所有多环境部署的系统；所有有外部依赖或可调参数的组件
- **判断依据**：能回答三个问题就算站住——**这个值在不同环境一样吗**（划配置/代码的线）？**它属于哪个层级**（决定审批与回滚要求）？**它能被谁改、改动留痕在哪**（决定可审计性）
- **配套**：启动时校验、密钥走独立通道、配置变更纳入[可观测性](observability.md)（变更事件与故障时间关联）、环境间差异清单化
