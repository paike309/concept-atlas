## 一句话定义

**中文**：让数据库结构变更与已部署的代码版本能够共存并安全演进的做法——版本化迁移脚本加一个兼容期。

**English**: Evolving database structure safely alongside already-deployed code, through versioned migration scripts and a compatibility window.

## 我的理解

**schema 迁移的本质是"两个版本共存"的问题，而不是"改表结构"这个动作。**

因为发布从来不是瞬时的：旧代码还在跑、新代码刚上线、回滚随时可能发生。**只要存在新旧代码同时运行的窗口，这个窗口里的数据就必须对两个版本都合法。** 这条推论直接给出全部做法：**破坏性变更必须拆成多步、跨多次发布完成。**

和普通代码变更相比，有两条性质上的差别必须记住：

1. **代码可以回滚，数据不行。** 删掉的列、转换过格式的行，回滚代码也回不来。所以"可回滚"在这里的含义是**向前兼容 + 不丢数据**，而不是"写了一个 down 脚本"。
2. **迁移与代码发布顺序强耦合。** 顺序错了就出事故——这是它比一般重构更需要编排的原因。

## 核心机制

**扩展 — 迁移 — 收缩（expand / migrate / contract）**，破坏性变更的标准三步：

| 步骤 | 做什么 | 为什么不能跳 |
|---|---|---|
| 1 扩展 | 新增列或新表（可空、有默认值），旧代码完全不受影响 | 此时新旧代码都能写 |
| 2 迁移 | 双写 + 回填历史数据 + 校验一致 | 这一步耗时最长，必须限速、分批、可中断 |
| 3 收缩 | 读切到新结构，确认**不再需要回滚**后删除旧列 | 提前删 = 回滚时旧代码找不到列 |

**兼容性判断**（与[契约设计](contract-design.md)同源，但对象是数据不是接口）：

| 变更 | 是否兼容 |
|---|---|
| 加可空列 / 加带默认值的列 | 兼容 |
| 加索引 | 兼容（但要关注锁与耗时） |
| 改列类型或含义 | **破坏** |
| 加 NOT NULL 约束到已有列 | **破坏**（存量数据可能不满足） |
| 删除列 / 重命名列 | **破坏** |

**大表迁移的工程约束**（这一块最容易被低估）：

- 某些数据库对"带默认值的加列"会**重写整表**，并在此期间持有强锁
- 加索引在大表上可能长时间占用 IO 甚至阻塞写入，需要支持在线建索引的方式
- 回填必须**分批 + 限速**，否则会打满 IO、拖垮线上查询，也会导致复制滞后
- 迁移脚本应能在**空库**与**已有数据的库**上都被验证（CI 里各跑一遍）

**版本记录**：用迁移表记录已应用的版本号，脚本一旦执行过就不再修改内容（改动等于让不同环境的状态不可复现）。这一点与[可复现构建](reproducible-build.md)是同一条纪律。

## 边界：它不是什么

- **与[契约设计](contract-design.md)的区别**：接口契约面向**调用方**（你能依赖什么），schema 迁移面向**同一份数据的多个代码版本**（新旧能否共存）。两者都讲兼容性，但约束的对象不同。
- **与备份的区别**：备份是出事后的恢复手段，迁移方案是**避免出事**的编排。有备份也不能随意改表——恢复的代价是停机与一段数据丢失窗口。
- **与"ORM 自动同步表结构"的区别**：开发期自动同步很方便，但生产环境的破坏性变更需要显式流程。**自动同步工具通常无法表达"跨两次发布"的意图**，而这恰恰是正确做法。
- **与数据修复脚本的区别**：迁移改的是**结构**，修复改的是**内容**。两者常同时需要，但验证方式不同——前者看新旧代码是否都能跑，后者看数据是否满足不变式。

## 常见误解

1. **有 down 脚本就等于可回滚** → 数据已删或已转换，down 脚本救不回来。真正的回滚能力来自"不破坏兼容性"。
2. **迁移可以在一个发布窗口内做完** → 大表回填可能持续数小时到数天，必须设计成可中断、可续跑。
3. **测试环境跑通就没问题** → 生产的**数据量、锁竞争、复制延迟**都不是测试环境能复现的，这三样恰好是事故来源。
4. **加一个 NOT NULL 且带默认值的列是无害操作** → 视数据库实现，可能触发整表重写并长时间持锁。
5. **迁移脚本和业务代码一起发最省事** → 顺序耦合被隐藏了，一旦需要回滚业务代码，数据库已经改到旧代码不支持的状态。

## 应用场景

- **该小步走**：所有生产库的结构变更，尤其是不可逆的那些
- **判断依据**：写下两句话——"**这条迁移在旧代码还在跑时执行，会怎样**"；"**回滚代码后，新写入的数据还能被旧代码读吗**"。两句都能答，才动手
- **配套**：迁移脚本进版本控制、进 CI（空库与有数据各跑一遍）、有独立的发布编排（不与业务代码同一批上线）
