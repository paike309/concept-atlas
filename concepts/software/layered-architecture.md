## 一句话定义

**中文**：把系统按抽象层次切分（表现层、应用层、领域层、基础设施层），并规定层间依赖方向的结构风格。

**English**: Structuring a system into abstraction layers — presentation, application, domain, infrastructure — with a defined direction of dependency between them.

## 我的理解

分层的真实目的不是"整理目录"，而是**控制改动的影响半径**：改界面不该动到业务规则，换数据库不该改业务规则。

分层的成败取决于**依赖方向的执行程度**，而不是层的数量。

很多项目名义上有四层，实际上领域层直接 import 了 ORM 的注解或框架基类——**依赖方向已经破了，分层只剩目录形状**。这时候换数据库照样要改业务代码，分层没有带来任何收益。

层的数量该多少？判断依据是**变化速率**。变化快、变化原因不同的部分应该分开；两层如果总是同时变，合成一层反而更好。

## 核心机制

**经典四层的职责**：

| 层 | 职责 | 不该包含 |
|---|---|---|
| 表现层 | 输入输出转换、协议适配 | 业务规则 |
| 应用层 | 用例编排（先做什么、后做什么） | 业务规则、持久化细节 |
| 领域层 | 业务规则与状态 | 编排、IO、框架依赖 |
| 基础设施层 | 持久化、消息、外部调用 | 业务规则 |

**最关键的一条区分：应用层 vs 领域层。**

- 应用层回答"做哪些步骤"
- 领域层回答"业务规则是什么"

混在一起的后果很具体：业务规则被编排放进服务方法里，既无法复用，也无法在不启动数据库的情况下测试。

**跨层通信**：跳过中间层（表现层直接调基础设施）是分层腐化的典型信号。

**与模块化的关系**：分层是**垂直**切分（按技术关注点），模块化是**水平**切分（按业务能力）。只做分层不做模块化，会得到"每层都很大"的系统；只做模块化不做分层，会得到业务逻辑与 IO 缠绕的模块。

**落地检查**：把内层代码的 import 列表拉出来看。出现框架、ORM、HTTP 客户端的名字，就说明方向破了。

## 边界：它不是什么

- **与微服务的区别**：分层是**代码内**的结构，微服务是**部署单元**的划分。二者正交——单体也能良好分层，微服务也能分层混乱。
- **与[依赖倒置](dependency-inversion.md)的区别**：分层规定"有哪些层"，倒置规定"依赖指向抽象"。分层不保证方向正确，倒置才保证。
- **与[端口与适配器](ports-and-adapters.md)的区别**：后者把应用核心视为**中心**而非顶层，视角不同，后果也不同（见那张卡）。

## 常见误解

1. **目录分好层就实现了分层** → 依赖方向破了就只是目录。
2. **层越多越清晰** → 层太多会产生大量无意义的透传代码，跳转成本上升。
3. **应用层和领域层可以合并** → 合并后业务规则与编排混在一起，测试与复用都变难。
4. **分层必须四层** → 层的数量由变化速率决定，不是配置项。

## 应用场景

- **该用**：需要长期维护、多人协作、业务规则有独立生命周期的系统
- **不该用**：纯数据透传服务、生命周期很短的脚本
- **判断依据**：检查两个信号——有没有跨层调用、领域层是否依赖了框架。任一命中，分层的收益基本没有兑现
