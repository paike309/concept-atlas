## 一句话定义

**中文**：按版本记录面向使用者（而非开发者）的变更说明。

**English**: A per-version record of changes written for users rather than for developers.

## 我的理解

定位是**面向使用者**的：他们关心"**升级会不会影响我**"，不关心你内部改了什么。

由此推出两条写作规则：

1. **面向影响而非实现**。"修复登录在 Safari 17 上失败"有用；"重构了 LoginService"没用
2. **按类型分组，而不是按提交顺序**。使用者是按"我在意哪类"来读的

一个常见错误是**用 commit log 代替 changelog**。两者读者不同、粒度不同：commit 面向开发者、粒度细；changelog 面向使用者、粒度粗。**自动把 commit 摘要拼成 changelog，通常得到一堆无意义条目。**

还有一个最容易被漏掉的部分：**弃用（Deprecated）。**

这是变更日志里最有价值的一类——它给出**迁移窗口**，让使用者有时间应对。**跳过弃用直接破坏，是变更管理里代价最高的做法。**

## 核心机制

**标准分类**：Added / Changed / Deprecated / Removed / Fixed / Security。

**与版本号的配合**：破坏性变更对应主版本，同时应在日志中**显式标注**"破坏性变更"（见[语义化版本](semantic-versioning.md)）。

**"未发布"区段**：把即将发布的变更放在顶部，发布时改名并加日期。这样开发过程中就在积累，不必事后回忆。

**链接**：每条变更关联到 issue 或 PR，便于追溯——这是审计链的一环。

**与 [ADR](adr.md) 的分工**：changelog 记录"**变了什么**"，ADR 记录"**为什么这么选**"。

## 边界：它不是什么

- **与 commit log 的区别**：读者与粒度都不同。可以自动辅助，但不能替代。
- **与 [ADR](adr.md) 的区别**：变更记录 vs 决策记录。两者互补。
- **与发布说明的区别**：release notes 可以更偏向宣传；changelog 应保持**事实性、可检索**。

## 常见误解

1. **用 commit log 自动生成就够了** → 读者不同，得到的是噪音。
2. **只记新增功能** → 修复与弃用对使用者更重要。
3. **内部重构也要记** → 使用者不关心，除非影响行为。
4. **格式自由** → 格式一致才能被依赖方快速扫描。

## 应用场景

- **该做**：任何被外部依赖的库或服务
- **判断依据**：问"**一个使用者要判断这次升级是否安全，看这份文档够不够？**" 不够，就说明写的是内部视角
- **配套**：与版本号一起构成兼容性承诺的对外表达
