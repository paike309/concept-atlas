## 一句话定义

**中文**：用「主版本.次版本.修订号」表达兼容性契约的版本命名约定——不兼容改动升主版本，兼容的新增升次版本，兼容的修复升修订号。

**English**: A versioning convention where major/minor/patch encode compatibility: breaking change, backward-compatible addition, backward-compatible fix.

## 我的理解

它的价值不在"编号好看"，而在于**把兼容性承诺变成可机器判断的规则**。

有了它，依赖方可以**不读你的变更日志**就决定"能不能安全升级"——依赖解析器读的只有版本号。

关键点：**版本号表达的是对外契约的变化，不是代码的变化量。**

- 重构一千行但接口不变 → 修订号
- 改一行但删了一个参数 → 主版本

很多团队出错在这里，把版本号当成"改动大小的计量"。这个误解的直接后果是**虚标**，而虚标的代价由下游承担：依赖解析器会自信地把一个破坏性版本升上去，然后下游在运行时崩溃。

另一个常被忽视的部分：**0.x 版本在规范里没有稳定契约**。这意味着依赖 0.x 的库时，次版本升级就可能是破坏性的。生产系统依赖 0.x 是一个明确的风险点，应该在依赖清单里被识别出来。

## 核心机制

**三个数字的判定依据**——问的是"对公共 API 的影响类型"，不是"改了多少代码"：

| 情形 | 升哪个 |
|---|---|
| 删字段、改语义、加必填、改默认行为 | 主版本 |
| 新增可选字段、新增端点 | 次版本 |
| 修复行为、性能优化、内部重构 | 修订号 |

**什么算公共 API**：被文档承诺的、被外部调用的部分。内部实现不算——**前提是你能划清内部与公共的边界**。划不清，就只能全都算。

**预发布与构建元数据**：`1.2.0-alpha.1`、`1.2.0+build.123`。表达稳定性与构建信息，不参与默认的优先级比较。

**与依赖解析的关系**：范围声明（`^`、`~`）依赖版本号如实反映兼容性。**虚标版本会直接导致下游运行时崩溃**，而且错误现场在下游，排查成本高。

**与变更日志的配合**：版本号给结论，变更日志给细节。两者缺一不可——只有版本号，下游不知道该不该关心；只有日志，机器无法判断。

**与分支策略的配合**：需要同时维护多个主版本时，必须有对应的长期维护分支。这是多版本产品复杂度的主要来源。

## 边界：它不是什么

- **与变更日志的区别**：版本号是标记，日志是说明。
- **与发布节奏的区别**：版本号不表达时间或新旧，只表达兼容性。0.1.0 不是"比 1.0.0 旧"，而是"没有稳定契约"。
- **与内部版本号的区别**：语义化版本面向**公共契约**。内部构建号属于另一套体系。

## 常见误解

1. **改动大就升主版本** → 看的是**兼容性**，不是改动量。
2. **内部实现可以随便改** → 前提是能划清内部与公共的边界，否则等于在赌。
3. **0.x 也在遵守语义化版本** → 规范明确 0.x 无稳定契约。依赖它就要接受次版本升级可能破坏。
4. **版本号不重要，看变更日志就行** → **依赖解析器只看版本号，不看你的日志。**

## 应用场景

- **该用**：任何被外部依赖的库或服务接口
- **判断依据**：试着写下"**这个版本允许下游做哪些假设**"。写不出来，说明版本号没有承载信息
- **配套**：与[契约测试](contract-testing.md)配合，把"有没有破坏契约"从人工判断变成 CI 检查

## 自测

1. 重构大量代码但接口不变，该升哪个数字？反过来，改一行但删掉一个参数呢？
2. 为什么 0.x 是风险点？生产系统依赖 0.x 库时应该做什么？
3. 虚标次版本号会在什么时候、在哪一方暴露问题？
