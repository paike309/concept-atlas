## 一句话定义

**中文**：认证确认"你是谁"，授权决定"你能做什么"——两步独立，合并判断会同时失去两边的保证。

**English**: Authentication establishes who a principal is; authorization decides what that principal may do — two separate steps whose conflation weakens both.

## 我的理解

**最常见的系统性错误，是把这两件事合成一个判断**——"登录了就允许"。

拆开之后，问题立刻变得可检查：

- 认证回答：**凭据是否有效**（可能失败、可能被劫持、可能需要多因素）
- 授权回答：**这个主体、对这个资源、做这个动作，是否被允许**（三者缺一都不算判过）

由此得到两条实践原则：

1. **默认拒绝，显式允许。** 允许列表应当是穷举的。默认放行的策略在新增接口时会**自动放行所有没考虑过的情况**——新接口往往是漏洞的入口，而默认拒绝至少会让新接口"默认不可用"，这个错误是安全的。
2. **授权判定必须在服务端、在每次请求上做。** 客户端状态（隐藏按钮、前端路由拦截）不构成授权——**它们只是用户体验，不是安全边界**。

还有一条容易被忽略的：认证的强度不只取决于密码规则，更取决于**凭据泄露之后能不能被滥用**——多因素、速率限制、会话失效、凭据不进日志，这几项合起来才是实际强度。

## 核心机制

**认证方式与其代价**：

| 方式 | 失效能力 | 代价 |
|---|---|---|
| 服务端会话（cookie + 会话存储） | 可即时失效 | 需要共享存储，横向扩展有状态 |
| 令牌（JWT 等无状态） | **默认无法即时失效** | 需要短有效期 + 刷新令牌，或维护黑名单 |

**一个高频术语错误**：OAuth 2.0 是**授权委托**框架（让第三方应用代表用户访问资源），**不是认证协议**。所谓"用 OAuth 登录"，实际是 OIDC 提供的认证层。把 OAuth 当认证用，是历史上多起漏洞的根源。

**密码存储**：加盐 + **慢哈希**（bcrypt / scrypt / Argon2），不是 SHA-256 这类快哈希。快哈希在 GPU 上可以每秒尝试数十亿次。

**多因素（MFA）**：知识、持有、固有三类中至少两类。**同类的两个因素不构成 MFA**（"密码 + 密保问题"仍是一类）。

**会话安全要点**：`HttpOnly`、`Secure`、`SameSite`；登录后**更换会话标识**（防会话固定）；同时设置空闲超时与绝对超时。

**授权模型的常见选择**：

| 模型 | 形态 | 典型问题 |
|---|---|---|
| RBAC | 角色 → 权限 | 角色爆炸、角色与组织边界脱节 |
| ABAC | 属性 + 策略 | 灵活但难以审计"谁能访问什么" |
| ReBAC | 关系（如"所属团队"） | 需要关系数据可查且一致 |

**授权绕过的三个高频成因**：直接以资源 ID 访问（IDOR）、只检查了"已登录"而没检查资源归属、批量接口漏检（单个接口有检查，批量导出没有）。

## 边界：它不是什么

- **与[权限与最小授权](../agent/least-privilege.md)的区别**：那张卡讲的是**策略**——给 Agent 与工具限定最小的权限范围；这张讲的是**机制**——谁是谁、能做什么的判定如何实现。策略要靠机制落地，机制再完备也挡不住过宽的授权。
- **与[加密](encryption-and-key-management.md)的区别**：加密保护数据传输与存储的过程；认证授权决定谁可以访问。**有密钥不等于有权限**——加密不能替代授权。
- **与审计日志的区别**：日志用于**事后发现**，不是访问控制。只有日志没有控制，等于"事后才知道被访问过"。
- **与"输入校验"的区别**：校验处理的是数据形状，授权处理的是访问资格。两者都在信任边界上，但一个管"数据能不能进来"，一个管"人能不能进来"。

## 常见误解

1. **认证和授权是一件事** → 混在一起就只剩"登录了"，资源级检查会系统性缺失。
2. **JWT 无状态，所以不用管失效** → 注销、改密、降权都要求失效能力，无状态只是把这份工作转移给了你。
3. **隐藏了 UI 元素就等于授权** → 接口才是边界，前端只是展示。
4. **OAuth 2.0 是认证协议** → 它是授权委托框架，认证由 OIDC 提供。
5. **密码复杂度够高就能防住** → 撞库、钓鱼、复用与密码复杂度无关。
6. **ID 不可猜测就是安全** → 不可猜测是隐蔽性，不是授权。

## 应用场景

- **该做**：所有多用户系统、所有对外接口（包括内部服务之间——内网默认可信是横向移动的起点）
- **判断依据**：对每个接口问三句——**谁在调用**（认证）、**他有没有权限对这个资源做这个动作**（授权）、**这个判断落在服务端哪一行代码**
- **配套**：认证端点的速率限制、凭据不进日志、授权失败与认证失败要能在[可观测性](observability.md)里区分（前者通常是配置问题，后者通常是被攻击）
