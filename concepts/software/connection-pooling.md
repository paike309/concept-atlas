## 一句话定义

**中文**：用有限数量的数据库连接服务远多于该数量的并发请求，并为过载时的等待与拒绝定义明确策略。

**English**: Serving far more concurrent requests than the number of available database connections, with an explicit policy for waiting and rejection under overload.

## 我的理解

连接池的存在理由有两层，**第二层才是关键**：

1. 连接是昂贵的——建连接要走网络往返、认证、服务端分配资源，量级在毫秒级；池化后取出通常只要微秒级。
2. **数据库能承受的并发连接数远小于应用的并发请求数。** 所以池的作用不只是"复用"，更是**在应用与数据库之间放一个显式的并发上限**。

由此推出两条反直觉但重要的结论：

- **池大小不该按并发请求数配，而该按数据库的处理能力配。** 请求多于池容量时，正确的处理是排队或拒绝（见[背压](backpressure.md)），而不是把池开大。
- **池太小是排队，池太大是雪崩——后者更难恢复。** 池太大意味着请求全部涌进数据库，在高并发下它大部分时间花在上下文切换与锁竞争上，而不是有效工作。**限制并发往往让总吞吐更高**，这正是池大小存在上限的原因。

还有一条硬要求：**池必须同时具备"有界 + 有获取超时 + 有拒绝策略"三件套。** 缺了获取超时，池满时上游线程会全部挂住等待，**故障从数据库扩散到整个应用**。

## 核心机制

**成本模型**：

| 动作 | 量级 |
|---|---|
| 建立一条数据库连接 | 毫秒级（网络往返 + 认证 + 服务端资源分配） |
| 从池中取一条空闲连接 | 微秒级 |
| 连接耗尽时的等待 | 不确定，取决于池配置与负载 |

**池大小与吞吐的关系不是线性的**：从很小增加时有明显收益，超过某一点后等待与竞争吃掉收益，继续增大反而使**尾延迟上升**。合理起点是"数据库可用核心数的一个小倍数"，再按实际 IO 等待比例与实测调整——**不按请求量调**。

**关键配置项**（各实现命名不同，含义相通）：

| 配置 | 作用 | 缺失的后果 |
|---|---|---|
| 最大连接数 | 上限 | 无界并发压垮数据库 |
| 获取连接超时 | 等不到就放弃 | 线程耗尽，故障向上扩散 |
| 最大生命周期 | 定期重建连接 | 长连接被中间设备或服务端掐断后报错 |
| 空闲回收 | 释放闲置连接 | 空闲连接白占数据库的额度 |

**必须做的一笔算术**：

```
应用实例数 × 每实例池上限  <  数据库的连接数上限
```

横向扩容时这个乘积会同步变大——**这就是"加机器反而把数据库打挂"的常见原因**。数据库侧通常还需要为管理连接与复制连接预留额度。

**过载时的行为链条**：池满 → 请求排队 → 延迟整体上升 → 触发超时 → 请求集中失败。**这与超时、重试、熔断是同一套问题**：没有超时，排队会一路传导到用户；有超时但重试无上限，失败会被重试放大。

**该观测的三个指标**（比"当前连接数"有用得多）：池占用率、**获取连接的等待时间**、活跃与空闲连接分布。其中等待时间是过载的最早信号。

## 边界：它不是什么

- **与[背压](backpressure.md)的区别**：背压是"把压力传递给上游"的机制，连接池是压力的一个**观察点与限制点**。有连接池不等于有背压策略——池满之后是无限等待、快速失败还是降级，是一个必须显式做出的决策。
- **与线程池的区别**：两者常被混为一谈。线程池限制**本进程的计算并发**，连接池限制**对下游的并发**。**池大小错配的典型症状就是：线程都在等连接**，此时调大线程池只会让等待更长。
- **与连接复用（HTTP keep-alive）的区别**：思路相同、层次不同。数据库连接还带**会话状态**（事务、临时表、会话变量），所以归还时必须确保状态被清理，否则会串味。

## 常见误解

1. **池越大越好** → 超过数据库处理能力后吞吐下降、尾延迟上升，且故障时更难恢复。
2. **池大小按并发请求数配** → 请求量该由排队与限流处理；池大小按数据库能力配。
3. **用了连接池就不需要超时** → 没有获取超时的池是故障放大器。
4. **池满只是变慢** → 池满 + 无超时 = 线程耗尽，整站不可用。
5. **扩容加实例总能提升吞吐** → 实例数 × 池大小的乘积会打满数据库连接上限。

## 应用场景

- **该做**：所有直连数据库的应用，尤其多实例横向扩展的
- **判断依据**：算两笔账——**实例数 × 池上限** 是否小于数据库连接上限；高峰时**获取连接的等待时间**是否显著上升。任一告警，都说明问题在连接层而不在业务逻辑
- **配套**：池的等待必须有超时；超时后要么快速失败，要么配合[熔断与降级](circuit-breaker.md)
