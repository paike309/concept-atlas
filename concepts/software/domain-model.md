## 一句话定义

**中文**：用对象与关系表达业务概念与规则，并让业务规则集中在领域对象里的建模方式。

**English**: Modeling business concepts and rules as objects and relationships, with the rules living inside those objects.

## 我的理解

领域模型与"数据模型"的差别在于**行为放在哪**。

- 数据模型：对象只是数据的容器，规则写在服务方法里
- 领域模型：规则跟着数据走（"订单不能修改已发货的条目"写在订单对象上，而不是散落在各处服务里）

实际后果是**规则的可发现性**：改业务规则时，规则集中在领域对象里你就只看一个地方；散落在服务层，你就得全库搜索。

但要提醒一句：**领域模型不是所有系统的正确答案。**

它适合业务规则复杂、频繁变化的系统。对于以数据搬运转发为主的系统（表单、报表、集成），领域模型会带来大量无意义的映射与转换代码——**这种系统用简单的数据模型加服务层更合适。**

## 核心机制

| 构件 | 含义 |
|---|---|
| 实体 Entity | 有身份，状态变化但身份不变 |
| 值对象 Value Object | 无身份，按值比较 |
| **聚合 Aggregate** | 一致性边界，外部只能通过聚合根访问 |
| 领域服务 | 跨实体的业务规则 |

**聚合的关键作用是定义事务边界**：一个聚合内的不变式由一次事务保证；跨聚合的一致性只能是最终一致。这一条决定了系统的并发行为与失败恢复方式，是设计中最需要想清楚的地方。

**与持久化的关系**：领域对象不应包含持久化细节（ORM 注解、框架基类），否则依赖方向反转，破坏分层的收益（见[分层架构](layered-architecture.md)）。

**通用语言**：模型中的名字必须与业务方使用的词一致。名字一旦脱节，模型会逐渐偏离业务，最后变成没人维护的翻译层。

**贫血模型**：只有 getter/setter 的对象 + 服务层里的全部规则。**问题不在"没有方法"，而在规则没有归属。**

## 边界：它不是什么

- **与数据模型的区别**：领域模型**有行为**，数据模型只描述存储结构。
- **与分层的区别**：领域模型是**层内的建模方式**；分层是层的划分。两者正交。
- **与 DTO 的区别**：DTO 是**跨边界传输**用的数据结构，不含规则。把 DTO 当领域模型用，会把规则重新推回服务层。

## 常见误解

1. **领域模型等于一堆实体类** → 关键在**规则的归属**，不在类的数量。
2. **必须用到全部构件** → 只建需要的。小系统里实体 + 值对象往往就够。
3. **它适合所有项目** → 规则简单的系统里它是纯负担。
4. **有了领域模型就不用服务层** → 应用层的**编排**仍然需要，只是不再承载业务规则。

## 应用场景

- **该用**：规则复杂且频繁变化、需要与业务方对齐术语、长期维护的核心系统
- **不该用**：数据搬运为主、生命周期短的系统
- **判断依据**：问"**规则改动时，你需要改几个文件？**" 超过三四个且散落在不同层，说明规则没有归属
