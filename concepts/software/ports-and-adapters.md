## 一句话定义

**中文**：把应用核心放在中心，外部世界通过「端口」（核心定义的接口）与「适配器」（具体实现）接入的结构风格。

**English**: A structure that places the application core at the centre, with the outside world connecting through ports (interfaces the core defines) and adapters (their implementations).

## 我的理解

它与分层的区别在于视角：**分层把业务放在最上面，端口与适配器把业务放在最里面。**

这个差别有实际后果：分层结构里，业务仍然"知道"上层存在（虽然不依赖）；而在端口与适配器结构里，业务只知道自己的端口，**驱动它的是谁（HTTP、定时任务、消息、测试）完全无关**。

于是同一套业务逻辑可以被完全不同的入口驱动——这也正是它让业务逻辑容易测试的原因。

说到底，「端口」就是[依赖倒置](dependency-inversion.md)在系统边界上的落地：**接口由内层定义，适配器在外层实现。**

**主次端口的区分很实用**：

| 类型 | 含义 | 例子 |
|---|---|---|
| 驱动端口（driving） | 谁调用我 | HTTP、CLI、定时器、消息消费者 |
| 被驱动端口（driven） | 我需要什么 | 存储、消息、外部 API |

两侧都要适配器，但方向相反。

## 核心机制

**端口**：内层定义的接口。驱动端口描述"我能被怎么调用"，被驱动端口描述"我需要对方做什么"。

**适配器**：把外部协议翻译成端口调用的代码。**一个端口可以有多个适配器**——生产用数据库，测试用内存实现。

**依赖方向**：所有依赖箭头指向中心；**中心不 import 任何外部技术**。

**与依赖注入的关系**：适配器通过注入进入核心；由装配层（容器或手工）决定选哪个适配器。

**落地形态**：核心包不依赖任何框架或 ORM；序列化、事务、重试这类横切关注点放在适配器层。

**与分层结构的换算**：应用层 + 领域层 ≈ 核心；表现层 + 基础设施层 ≈ 适配器。所以迁移成本通常不高，难的是坚持依赖方向。

## 边界：它不是什么

- **与分层的区别**：见「我的理解」。中心与顶层的差别会在依赖方向的处理上具体体现出来。
- **与依赖倒置的区别**：倒置是**原则**，端口与适配器是该原则在系统边界上的**一种具体组织方式**。
- **与整洁架构 / 洋葱架构的区别**：同源，术语不同，层次命名略有差异。

## 常见误解

1. **就是换个名字的分层** → 业务处在中心还是顶层，决定了它能不能脱离入口独立测试。
2. **每个类都要有端口** → 只为**需要替换或隔离**的边界建端口。给内部协作类建端口只是增加间接层。
3. **适配器只是薄薄一层转发** → 它承担协议转换、错误映射、事务边界，是有实质责任的一层。写成无脑转发，错误信息就会失真，进而导致模型/调用方误判。
4. **用了六边形就不用管核心内部结构** → 核心内部仍然需要组织方式（分层或模块化）。

## 应用场景

- **该用**：业务逻辑需要在多种入口（API、批处理、事件）下复用；需要在测试中替换外部依赖；多个外部系统的协议差异大
- **判断依据**：问"**核心逻辑能否在不启动任何外部组件的情况下测完**"。不能，就说明边界没画出来
- **不该用**：纯粹的数据透传服务——没有值得保护的核心
