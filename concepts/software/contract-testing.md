## 一句话定义

**中文**：验证两个组件对它们之间接口的理解是否一致的测试，通常由使用方（消费者）驱动。

**English**: Tests that verify two components agree on the meaning of the interface between them, typically driven by the consumer side.

## 我的理解

契约测试填补的是[测试金字塔](test-pyramid.md)中间的一处真空：

- 单元测试保证"我的逻辑对"
- 端到端测试保证"整体能跑"
- **没人保证"我发给你的字段，你确实按这个含义理解"**

消费者驱动的做法是：**由使用方声明它期望什么，提供方验证自己满足这些期望。**

方向很关键。由消费者定义，才不会出现"提供方测了自己以为的接口，但其实没人这么用"这种自嗨式验证。

它的性价比很高：比端到端快、比单元测试更能发现真实的集成问题。而且它把"接口变更会不会破坏下游"变成了一件**可以在提供方 CI 里自动检查**的事。

## 核心机制

**契约包含什么**：

- 请求的形状（路径、方法、必需字段）
- 响应的必需字段与**含义**
- 错误码语义
- 边界值约定

**生成与验证的流程**：

1. 消费者测试运行时生成契约文件
2. 契约文件发布到共享位置（仓库或契约代理）
3. 提供方在 CI 中用该文件运行验证测试
4. 提供方破坏契约 → CI 失败，无法合并

**版本与兼容**：契约也要版本化。破坏性变更（删字段、改含义、加必填项）需要显式声明与协调。

**与 schema 的关系**：JSON Schema / Protobuf 可以表达**结构**，但**表达不了语义**——同一个 `timestamp` 字段，是"下单时间"还是"支付时间"，schema 说不出来。**契约测试覆盖的正是语义层面。**

**覆盖范围**：只覆盖双方**真正使用**的部分，不必覆盖接口全集。这也是它比端到端便宜的原因。

## 边界：它不是什么

- **与单元测试的区别**：是否跨越组件边界。
- **与端到端测试的区别**：端到端要启动完整系统与真实环境；契约测试不依赖真实环境，因此快且稳。
- **与 API 文档的区别**：文档是描述，契约是**可执行的断言**。**文档会过期，契约测试会失败。**

## 常见误解

1. **有接口文档就不需要契约测试** → 文档不执行、不报错、会过期。
2. **端到端能覆盖同样的问题** → 端到端慢、脆、定位差，且通常只覆盖少数路径。
3. **契约等于 schema** → schema 覆盖结构，不覆盖语义。
4. **契约由提供方定义更省事** → 由提供方定义会造出没人需要的接口契约，验证的是假想需求。

## 应用场景

- **该用**：跨团队或跨服务的接口；同一接口有多个消费者；接口变更频繁
- **不该用**：单一应用内部紧密耦合的模块（用单元测试与集成测试更直接）
- **判断依据**：问"**这个接口改了，我怎么知道有没有破坏别人？**" 答不出来就该引入契约
- **配套**：与[语义化版本](semantic-versioning.md)配合——契约告诉你有没有破坏，版本号告诉下游能不能安全升级

## 自测

1. 契约测试填补的是哪一层与哪一层之间的空隙？用一个具体故障说明没有它会发生什么。
2. 为什么契约应由消费者定义？由提供方定义会产生什么后果？
3. 契约能表达 schema 表达不了的什么东西？举一个例子。
