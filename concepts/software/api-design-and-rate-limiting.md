## 一句话定义

**中文**：选择接口的表达风格，并明确约定调用方可以以多快的速度使用它。

**English**: Choosing how an API is expressed, and specifying how fast callers are allowed to use it.

## 我的理解

**风格取舍不是"先进与落后"，而是"用哪些约束换什么能力"。**

| 风格 | 主要收益 | 主要代价 |
|---|---|---|
| REST | 统一的资源语义 → 可被通用工具与中间层理解（缓存、鉴权、监控） | 复杂查询/聚合表达别扭 |
| RPC | 调用直观、契约强类型 | 通用中间层难以理解语义，缓存等能力要自己做 |
| GraphQL | 客户端自由取数，一次请求拿到多形态数据 | **HTTP 层缓存基本失效**，服务端复杂度与查询成本控制成为新问题 |

更实用的一条判断：**风格选得"不够时髦"通常能活下去，而 HTTP 语义用错会持续制造故障。** 后者是真正要守住的底线——把写操作放进 GET（会被爬虫与预取触发副作用）、用 200 表达业务失败（监控与重试逻辑全部失真）、把非幂等操作标成可重试。**规范里对方法与状态码的定义不是形式，它决定了第三方工具能不能正确对待你的接口。**

第二部分（限流）的核心认识是：**限流不只是保护自己，它同时是对调用方的契约。**

- 只保护不告知 → 客户端只能靠试错摸边界，**失败模式变成"随机被拒"**
- 明确告知边界与退让方式 → 客户端可以自我调节，整体更稳定

所以限流的完整形态是"**限制 + 可预期的拒绝信号 + 客户端遵守的退让规则**"，三者缺一，限流都会变成新的故障源。

## 核心机制

**HTTP 方法与幂等性**（这是重试能否安全的前提，见[幂等性](idempotency.md)）：

| 方法 | 幂等 | 说明 |
|---|---|---|
| GET / HEAD | 是 | **只读语义**；被预取、缓存、爬取是正常行为 |
| PUT / DELETE | 是 | 重复执行结果相同 |
| POST | **否** | 每次通常产生新资源 |

**状态码的语义分工**：2xx 成功、4xx 调用方问题（**不要拿它表示服务端故障**）、5xx 服务端问题。两个与限流直接相关：

- **429 Too Many Requests**：明确表示"被限流"（RFC 6585 定义）
- **`Retry-After`**：告诉客户端多久之后再来。**缺少它，客户端只能盲目重试**——而盲目重试正是限流场景下最常见的自伤行为

**四种常见限流算法**：

| 算法 | 特点 | 问题 |
|---|---|---|
| 固定窗口 | 实现最简单 | **窗口边界可产生双倍突发** |
| 滑动窗口 | 更平滑 | 需记录时间分布，成本更高 |
| 令牌桶 | **允许一定突发**，平均速率受控 | 参数需要按实际业务调 |
| 漏桶 | 输出速率恒定 | 不允许突发，可能增加延迟 |

**限流的多层次**：边缘网关（挡外部）、服务级（保护单服务）、租户/API key 级（公平性）、以及**按接口成本加权**（导出类重接口一次消耗更多额度）。**只在网关做限流是不完整的**——内部调用、多入口、以及绕过网关的路径都在外面。

**配额与限流的区别**：配额是**周期总量**（每月 100 万次），限流是**瞬时速率**（每秒 100 次）。两者常同时存在，解决的问题不同：配额管成本与商业模型，限流管稳定性。

**分布式限流的精度问题**：多实例各自计数会导致实际放行量是"实例数 × 单实例阈值"。共享计数（集中存储）更准确但引入延迟与单点；取舍取决于对精度的实际需求——**多数场景允许一定误差，但要知道误差存在**。

**客户端一侧的配合**：收到 429 后应**指数退避 + 随机抖动**。抖动的作用是避免大量客户端在同一时刻同时重试（**这是把限流升级为雪崩的经典路径**）。

## 边界：它不是什么

- **与[契约设计](contract-design.md)的区别**：契约定义"调用方可以依赖什么"，限流是**契约的一部分**——它承诺的是"你可以用多快"。**速率承诺没写清，契约就不完整。**
- **与[背压](backpressure.md)的区别**：背压是**系统内部**的压力传递（下游慢 → 上游感知并放缓），限流是**对外部调用方**的约束。前者是自适应机制，后者是事先约定的规则。
- **与[熔断](circuit-breaker.md)的区别**：两者方向相反——**熔断保护"我不被下游拖垮"（我不调用你），限流保护"我不被上游打垮"（不让你调用我）**。一个向外，一个向内。
- **与 API 网关的区别**：网关是**执行位置**，限流是**策略**。策略可以在网关、服务内或两者同时执行。

## 常见误解

1. **REST 比 RPC 先进** → 是取舍不是进化；缓存与通用工具的支持是 REST 的主要收益。
2. **用 GET 做写操作没关系** → 预取、爬虫、浏览器重试都会触发副作用。
3. **限流只在网关做就够** → 内部调用与多入口绕过网关，服务自身仍需保护。
4. **429 不返回 `Retry-After`** → 客户端只能盲试，重试风暴由此产生。
5. **客户端重试不需要抖动** → 同步重试会把限流升级为雪崩。
6. **阈值定一次就不用改** → 阈值应依据实际容量与[剖析](profiling.md)/压测结果调整。

## 应用场景

- **该做**：所有对外 API（含限流）；所有被多个调用方使用的内部服务
- **判断依据**：能回答三句——**每个调用方可以用多快**？**超限时会收到什么信号**？**他应该怎么退让**？
- **配套**：与[超时、重试与退避](timeout-retry-backoff.md)配合（客户端按退避重试）；与[可观测性](observability.md)配合（限流命中率、被拒客户端的分布）；限流维度要与[认证](authentication-and-authorization.md)身份对齐（按调用方而非只按 IP）
