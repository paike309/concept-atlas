## 一句话定义

**中文**：自回归生成时缓存每层每头的 key 与 value，避免每生成一个 token 都重算整个前缀。

**English**: Caching the per-layer, per-head keys and values during autoregressive generation so each new token avoids recomputing the entire prefix.

## 我的理解

它存在的理由很朴素：生成是逐 token 的，而每生成一个新 token 都要对全部前缀做注意力。如果不缓存，第 n 个 token 要重算 n−1 次前缀，总计算量是 $O(n^2)$ 的**重复劳动**。

缓存之后，每个位置的 K/V 只算一次；新 token 只需拿自己的 query 去和缓存的 K 匹配。

**用显存换计算**——这是它唯一的取舍，也是它唯一的代价。

后果很直接：**显存随长度与并发线性增长**，成为长上下文服务的主要瓶颈（见[推理成本与显存估算](inference-cost.md)）。很多"长上下文部署跑不起来"的问题，根因都在这里。

## 核心机制

**缓存内容**：每层每头的 K 与 V。**不含 Q**——Q 只属于当前位置，用完即弃，缓存它没有意义。

**显存公式**：

```
KV 显存 ≈ 2 × 层数 × 头数 × 头维度 × 序列长度 × 精度字节 × 批大小
```

**为什么能省**：K/V 只依赖该位置的输入与权重，与后续 token 无关，因此可以复用。

**分页管理**：把缓存切成固定大小的块按需分配，减少内存碎片与预留浪费。这是 vLLM 一类推理引擎的核心优化。

**前缀缓存（prefix caching）**：相同前缀的请求可以复用缓存。固定系统提示场景下收益显著——同一段长系统提示不必每个请求重算一次。

**与批处理的关系**：并发越多，同时存活的缓存越多。这是**吞吐与显存的核心矛盾**。

## 边界：它不是什么

- **与[上下文窗口](context-window.md)的区别**：窗口是**模型能力上限**（由位置编码与训练决定）；KV Cache 是**推理实现的开销**。两者数值相关但性质不同——窗口决定"能处理多长"，缓存决定"跑起来要多少显存"。
- **与模型权重显存的区别**：权重是常数，缓存是变量。**长上下文下缓存可以超过权重。**
- **与训练时激活值的区别**：训练要保存全部层的激活用于反向传播；推理只需要 K/V，量小得多。

## 常见误解

1. **KV Cache 只影响速度** → 它主要影响**显存**，是长上下文服务的主要瓶颈。
2. **缓存会无限增长** → 它随序列长度增长，但对话结束后释放。并发下"同时存活的多份缓存"才是真问题。
3. **长上下文只要显存够就行** → 还有**带宽**瓶颈：每生成一个 token 都要读取整份缓存，这是 decode 阶段变慢的根因。
4. **可以随便截断缓存中间部分** → 位置编码与注意力结构对缺失位置敏感，截断需要配合专门机制。

## 应用场景

- **该算**：估算并发能力与部署成本；决定上下文长度上限
- **该用**：前缀缓存（固定系统提示、少样本示例固定的场景）
- **判断依据**：如果 decode 延迟随上下文增长而明显变慢，瓶颈大概率在缓存读取带宽，而非算力
