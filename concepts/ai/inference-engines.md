## 一句话定义

**中文**：负责把模型高效跑起来并对外提供服务的软件层——核心任务是在延迟、吞吐与显存之间做调度。

**English**: The software layer that runs the model efficiently and serves it — essentially scheduling among latency, throughput, and memory.

## 我的理解

引擎要解决的核心矛盾是：**显存有限，而请求的输入输出长度各不相同、到达时间随机。**

朴素的批处理（等一批凑齐再一起算）会带来严重的队头阻塞：一个长输出请求会拖住整批。所以现代引擎的关键技术是**连续批处理（continuous batching）**——每次前向都重新组批，完成的请求立刻退出，等待的立刻加入。

第二个关键点是**显存管理**。KV Cache 大小随长度变化，预分配会浪费、动态分配会碎片化。分页管理（把缓存切成固定块按需分配）是当前主流解法。

**分块预填充（chunked prefill）** 是第三项：把长输入的处理切成小块，与 decode 交错调度，避免一个长请求把其他请求的延迟拖坏。

这三项合起来决定了一台机器能服务多少并发、延迟分布长什么样。

## 核心机制

| 技术 | 解决的问题 |
|---|---|
| 连续批处理 | 队头阻塞，提高吞吐 |
| 分页 KV 管理 | 显存碎片与浪费 |
| 分块预填充 | 长输入的延迟干扰 |
| 前缀缓存 | 相同系统提示重复计算 |
| 投机解码 | decode 阶段的串行瓶颈 |
| 张量/流水并行 | 单卡装不下的大模型 |

- **prefill 与 decode 的资源特征不同**：prefill 算力密集，decode 带宽密集。**把两者混在同一批里会互相干扰**，这是分块预填充的动机
- **吞吐与延迟的取舍**：批越大吞吐越高、单请求延迟越长。SLA 决定这个平衡点
- **量化支持**：引擎是否支持某种量化格式，直接决定能否用上（见[量化](quantization.md)）
- **前缀缓存的适用条件**：系统提示固定、少样本示例固定时才有效

## 边界：它不是什么

- **与"模型"的区别**：引擎不改变模型能力，只改变资源利用率。**引擎不会让模型变聪明，也不会让不可行的方案变可行。**
- **与"API 服务"的区别**：API 层管鉴权、配额、路由；引擎管单机（或多机）的模型执行。
- **与"框架"的区别**：训练框架关注反向传播与并行策略；推理引擎关注前向的调度与显存。

## 常见误解

1. **换个更快的引擎就能解决问题** → 若瓶颈在方案本身（上下文过长、轮次过多），引擎优化只是延迟暴露。
2. **批处理越大越好** → 会牺牲单请求延迟，且可能超出显存。
3. **前缀缓存总是有效** → 只有前缀相同时才有效。
4. **引擎的吞吐数字可以直接对比** → 吞吐与延迟、序列长度分布强相关，脱离条件的吞吐数字没有可比性。

## 应用场景

- **该关注**：自建推理时；需要估算并发上限与成本时；量化格式选型时
- **不必深究**：调用托管 API 时——这些优化已经包含在单价里
- **判断依据**：先确定两件事——**目标延迟（P95）与目标并发**。两者定了，引擎参数才有意义；否则调参只是碰运气
