## 一句话定义

**中文**：把模型跑起来所需的显存、算力与金钱的量级估算方法——它的主要价值是在动手之前排除不可行的方案。

**English**: Methods for estimating the GPU memory, compute, and money required to serve a model — valuable mainly because it rules out infeasible designs before any implementation work.

## 我的理解

这一块最实际的作用不是"省钱"，而是**提前排除**。

"把整库文档塞进 128k 上下文"这类决定，不需要试，算一笔账就知道可不可行。跳过这一步的人，通常在实现阶段撞墙，然后误以为是"框架没选好"。

两个必须随身带的量级：

1. **权重显存 ≈ 参数量 × 每参数字节数**（FP16 是 2 字节，4-bit 量化约 0.5 字节）
2. **KV Cache 随上下文长度与并发数线性增长**，长上下文场景下它常常比权重还大

第 2 条是最容易被漏掉的。**决定你能不能真正服务的常常不是模型多大，而是上下文多长、并发多少。**

## 核心机制

**权重**：

| 模型规模 | FP16 权重 | 4-bit 量化 |
|---|---|---|
| 7B | ≈ 14 GB | ≈ 4 GB |
| 13B | ≈ 26 GB | ≈ 7 GB |
| 70B | ≈ 140 GB | ≈ 35 GB |

实际还要加激活值、中间缓冲，以及框架自身的预留（推理引擎通常按比例预留显存池）。工程上常按权重的 20%~30% 估这部分开销，但长上下文时它会被 KV Cache 掩盖，必须单独计算。

**KV Cache**（逐 token 生成时必须缓存每层每头的 key 与 value）：

```
KV 显存 ≈ 2 × 层数 × 头数 × 头维度 × 序列长度 × 精度字节 × 批大小
```

它随**序列长度线性**增长，也随**批大小线性**增长。所以并发一上来就容易爆——这也是长上下文服务贵的主要来源。

**两个阶段的成本结构不同**：

- **Prefill**（处理输入）：算力密集。长输入贵在这里
- **Decode**（逐 token 生成）：显存带宽密集。长输出贵在这里

这解释了为什么多数接口的"输出 token 单价"高于"输入 token"。

**吞吐优化的主要手段**：批处理、KV Cache 复用（前缀缓存）、量化、投机解码。注意：**批处理提高吞吐会牺牲单请求延迟。**

## 边界：它不是什么

- **与训练成本的区别**：推理是持续成本，训练是一次性成本。两者差几个数量级，混着谈会得出错误结论。
- **与模型大小的区别**：参数量只决定权重显存。**上下文长度与并发数决定能否真正服务。** 一个 7B 模型开满长上下文且高并发，显存压力可能超过一个 70B 模型的短上下文部署。
- **与延迟的区别**：显存装得下不等于快。延迟由 prefill 算力、decode 带宽、批大小共同决定，与容量是两回事。

## 常见误解

1. **参数量就是全部显存需求** → 漏掉 KV Cache 与激活。长上下文下 KV Cache 可能超过权重。
2. **本地跑 7B 只要 8GB 显存** → FP16 权重已经 14GB。8GB 只能跑 4-bit 量化且上下文很短。
3. **上下文翻倍只是慢一点** → 注意力计算约 4 倍，KV Cache 约 2 倍。
4. **成本问题靠优化框架解决** → 正确的顺序是先改方案（缩短上下文、减少轮次、检索前置），再谈框架优化。

## 应用场景

- **该算**：选型前、决定上下文长度前、决定是否自建推理前
- **可以不算**：调用托管 API 且量很小时，看单价即可
- **判断依据**：先写下三个数——单次调用的输入 token 数、输出 token 数、每天调用次数，乘单价得到量级。需要自建时再算显存
