## 一句话定义

**中文**：模型在一次前向计算中能读取的 token 数上限，输入与输出（在多数实现中）共享这个额度。

**English**: The maximum number of tokens a model can attend to in a single forward pass; in most implementations the input prompt and the generated output share this budget.

## 我的理解

关键要分清两件事：**窗口是"视野"，不是"记忆"**。

模型本身没有跨请求保留的状态。每一次调用都是拿当前这段 token 从头算一遍，算完就丢。你以为它在"记得"上一轮对话，其实是客户端把之前的消息重新拼进了这次的输入——是**重放**，不是回忆。

这个区分一旦立住，很多工程问题就变得显然：历史越长，每次重放的输入越大、越贵、越慢；而且超长之后模型对中间部分的利用率会下降，不是塞满就好。

窗口大小和 [Agent 循环](../agent/agent-loop.md) 直接相关：Agent 的每一步都要把工具返回值追加进上下文，多轮之后必然撞到上限。所以 Agent 工程的主要工作，本质上是**上下文预算管理**。

## 核心机制

**上限从哪来**：

1. **注意力复杂度**。$n$ 个 token 要两两算相关性，是 $n \times n$ 的矩阵（详见 [注意力机制](attention-mechanism.md)）。长度翻倍，计算量约 4 倍，注意力显存也约 4 倍。
2. **KV Cache 线性增长**。生成时缓存每一层的 key/value，显存占用正比于 层数 × 长度 × 维度 × 精度。这是长上下文推理显存的主要开销。
3. **位置编码外推能力**。训练时见过的位置范围之外，位置编码的表达会退化（详见 [Transformer 架构](transformer.md)）。所以"标称窗口"往往大于"有效窗口"。

**有效利用 ≠ 标称上限**：

- 位置偏差：开头和结尾的信息利用最充分，**中段最容易被忽略**（lost in the middle）。
- 干扰效应：无关内容越多，关键信息的召回率越低。
- 因此"把文档全文塞进去"通常不如"检索出相关段落再塞"。

**工程上的三种应对**：检索前置（RAG）、上下文压缩（摘要/剪枝）、任务拆分（把长任务拆成多个短调用）。

## 边界：它不是什么

- **与"记忆"的区别**：窗口是单次计算的范围；记忆是跨请求保留状态。目前的实现里后者靠外部机制（存文件、存库、在 prompt 里重放）实现，不是模型自带的。
- **与"训练数据量"的区别**：窗口是推理时可读的量，训练数据量是学过的知识规模。两者毫无关系——窗口再大也不会让模型知道训练时没见过的私有信息。
- **与"知识截止日期"的区别**：截止日期决定它"知道什么"，窗口决定它"这次能看多少"。模型知道的内容和你塞给它的内容，在它眼里都是上下文，但来源和处理方式不同。

## 常见误解

1. **窗口大 = 记得住** → 每次调用仍是无状态的。窗口大只意味着这一次能读得多。
2. **标称 1M 就能用满 1M** → 有效利用率显著低于标称值，且随长度衰减。要用满必须实测，不能信规格表。
3. **长上下文可以替代 RAG** → 长上下文解决"能放进去"，不解决"能找到、能排干扰、能控成本"。信息密度高、更新频繁的场景，检索仍然必要。
4. **往里塞的东西越多越安全** → 无关内容会稀释关键信息，还会引入注入风险（来自外部的文本可能被当作指令执行）。

## 应用场景

- **该用大窗口**：单次任务需要全局一致性（整份合同审阅、整库重构规划）、材料总量在几千到几万 token、调用次数少。
- **该用检索**：知识库规模远超窗口、内容频繁更新、需要在回答里给出出处、调用次数多所以成本敏感。
- **该用压缩**：多轮对话与 Agent 长任务。常用做法是保留系统提示 + 最近若干轮原文，中间部分摘要化。
- **判断依据**：先量出"单次调用需要多少 token、每天多少次、单价多少"，再决定策略。凭感觉选长窗口是最常见的成本失控来源。

## 自测

1. 一个模型标称 128k 窗口，为什么实测在 60k 输入时就已经明显漏掉中间信息？这属于实现缺陷还是预期行为？
2. 多轮对话里"模型记得我之前说的话"这个现象，按窗口的定义解释，机制上实际发生了什么？
3. 长上下文和 RAG 各自的成本结构是什么？各在什么调用频率下更划算？
