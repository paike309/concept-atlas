## 一句话定义

**中文**：在具体任务、成本与约束下选择模型与配置的决策方法。

**English**: Deciding which model and configuration to use, given the task, cost, and constraints.

## 我的理解

多数团队的选型是反着做的：先选定一个强模型，再想办法让任务适配它。

正确顺序是**先把任务的可验证标准定下来，再让模型来考**（见[评估方法论](evaluation.md)）。

四个维度必须一起看，单看任何一个都会选错：

| 维度 | 关键点 |
|---|---|
| 能力 | 在你的任务上够不够——不是基准分 |
| 成本 | 单价 × 单次 token × 调用次数；**输出单价通常更高** |
| 延迟 | 看 **P95**，不看平均值 |
| 可控性 | 能否私有部署、数据出境、**能否固定版本** |

**第 4 项最容易被忽略，后果却最严重。**

托管模型会**静默更新**。一个靠提示词反复调好的行为，可能在某次更新后失效，而且没有任何通知。对可复现性有要求的场景（评测基线、受审系统），这是一个必须显式处理的风险。

## 核心机制

**决策顺序**：定义任务 → 建立小规模评测集 → 横向比较 → 按成本与延迟筛选 → 最后看可控性。

**成本估算的三个数**（写不出来就还没法决策）：

1. 单次调用的输入 token 数
2. 单次调用的输出 token 数
3. 每天的调用次数

三者相乘得到量级。**很多方案在这一步就被排除**，不需要真的实现。

**分层路由**：简单请求走小模型、复杂请求走大模型。成本可显著下降，代价是需要一个可靠的复杂度判定——判定错了会同时损失成本和质量。

**版本漂移的对策**：

- 记录调用时的模型版本号
- 把评测集做成**回归测试**，定期重跑
- 对关键行为设置监控告警

## 边界：它不是什么

- **与基准排名的区别**：基准与你的业务分布不同，榜上表现不能替代任务内表现。
- **与微调的区别**：选型选的是**基座**，微调是在基座上的定制。基座选错了，微调救不回来。
- **与提示工程的区别**：先选对模型，再优化提示。顺序反了会浪费大量时间。

## 常见误解

1. **用最强的模型总是最省事** → 成本与延迟可能不可接受；且强模型的能力优势未必作用在你的任务上。
2. **基准分高就适合我的任务** → 分布不同。
3. **模型选定后不用再管** → 会静默更新，行为可能变化。
4. **自建一定更便宜** → 小规模下通常更贵（见[推理成本与显存估算](inference-cost.md)）。只有高利用率时才可能反超。

## 应用场景

- **该做**：任何生产系统上线前；任何成本敏感场景
- **判断依据**：写下那三个数，乘出月成本量级。**很多方案在这一步就被排除，不必先实现**
- **配套**：固定采样参数，否则无法区分"模型换了"和"运气好"（见[采样策略](sampling.md)）
